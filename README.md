# Support Reports

Внутренний инструмент для составления ежедневных support-репортов вместо ручного
копипаста в Telegram. Позволяет вести тикеты по группам, менять статусы,
писать заметки и одной кнопкой копировать готовый текст репорта.

## Стек

- **Next.js 16** (App Router) + TypeScript + Tailwind CSS
- **Prisma 7** (driver adapters) + PostgreSQL
- Личные аккаунты (свой пароль у каждого агента) + подписанная куки-сессия

## Локальный запуск

1. Установи зависимости:

   ```bash
   npm install
   ```

2. Настрой `.env` (уже создан локально, но не закоммичен — см. `.gitignore`):

   ```env
   DATABASE_URL="postgresql://USER@localhost:5432/support_reports?schema=public"
   AGENT_EROSH_PASSWORD="пароль-ероша"
   AGENT_ALPA_PASSWORD="пароль-алпы"
   AGENT_DEZHURNY_PASSWORD="пароль-дежурного"
   SESSION_SECRET="длинная-случайная-строка"
   TELEGRAM_BOT_TOKEN="токен-от-BotFather"
   TELEGRAM_WEBHOOK_SECRET="любая-случайная-строка"
   OWN_AGENT_TELEGRAM_IDS="123456789,987654321"
   # Опционально — см. "ИИ-описания тикетов" и "Поиск дублей" ниже.
   # Можно указать несколько ключей через запятую ("key1,key2") — при
   # ошибке/исчерпании квоты первого автоматически пробуется следующий.
   # Бесплатная квота Groq (100k токенов/день) висит на аккаунте целиком,
   # так что запасной ключ должен быть с другого аккаунта, не просто
   # второй ключ того же.
   GROQ_API_KEY="ключ-из-console.groq.com/keys"
   # Необязательно: модель Groq. По умолчанию openai/gpt-oss-120b.
   # Groq выводит модели из обращения (llama-3.3-70b-versatile, на которой
   # это писалось, отключена 16.08.2026) — тогда все ИИ-фичи разом молча
   # перестают работать, откатываясь на регулярки. Лечится сменой этой
   # переменной без деплоя: живой список — GET /openai/v1/models.
   GROQ_MODEL=""
   # Опционально — см. "Ревью и отправка репорта через Telegram" ниже
   AGENT_TELEGRAM_IDS="Ерош:123456789,Алпа:987654321"
   CRON_SECRET="длинная-случайная-строка"
   REPORT_TARGET_CHAT_ID=""
   # Только если в чате из REPORT_TARGET_CHAT_ID включены "Темы" и репорт
   # должен уходить в конкретную тему, а не в общий поток
   REPORT_TARGET_THREAD_ID=""
   # Опционально — инструмент смены почты ученику в основной платформе JUZ40
   # (см. "Смена почты ученику" ниже). Пока не заданы все три — страница и
   # пункт меню "Почта" скрыты, фича выключена.
   PLATFORM_API_URL="https://api.juz40-edu.kz"
   PLATFORM_SERVICE_USERNAME="сервис-аккаунт-платформы"
   PLATFORM_SERVICE_PASSWORD="пароль-сервис-аккаунта"
   ```

3. Накати миграции и засей дефолтные группы:

   ```bash
   npx prisma migrate dev
   npx prisma db seed
   ```

4. Запусти дев-сервер:

   ```bash
   npm run dev
   ```

   Открой http://localhost:3000, выбери свой профиль (Ерош / Алпа /
   Дежурный) и войди своим паролем.

## Деплой на Vercel

1. Запушь репозиторий в GitHub/GitLab и подключи его в Vercel (Import Project).
2. В Vercel Dashboard → **Storage** → **Create Database** → выбери **Postgres**
   (Neon) и подключи к проекту. Vercel сам добавит `DATABASE_URL` в переменные
   окружения проекта.
3. В **Settings → Environment Variables** добавь:
   - `AGENT_EROSH_PASSWORD` — пароль для входа под именем "Ерош"
   - `AGENT_ALPA_PASSWORD` — пароль для входа под именем "Алпа"
   - `AGENT_DEZHURNY_PASSWORD` — общий пароль для входа под именем
     "Дежурный" (для сменных/выходных саппортов). При входе под ним человек
     указывает своё имя (напр. "Тикош") — оно становится автором и попадает
     в заметку как "Тикош шешті"
   - `SESSION_SECRET` — длинная случайная строка (замени!)
   - `TELEGRAM_BOT_TOKEN` — токен бота от @BotFather (см. ниже)
   - `TELEGRAM_WEBHOOK_SECRET` — своя случайная строка для защиты вебхука
   - `OWN_AGENT_TELEGRAM_IDS` — Telegram id всех саппортов через запятую (в
     выходные допиши id сменных спецов), см. раздел "Свои сообщения не
     попадают во Входящие". Если она не задана, те же id берутся из
     `AGENT_TELEGRAM_IDS` (там они с именами) — забытая переменная иначе
     молча ломает всё, что опирается на "это наш агент", и выглядит это не
     как ошибка, а как будто фичи просто не работают
   - `GROQ_API_KEY` — опционально, только если хочешь включить ИИ-описания
     тикетов или поиск дублей (см. ниже); без него всё работает как раньше,
     на регулярках. Можно указать несколько ключей через запятую — при
     ошибке/429 у первого автоматически пробуется следующий (см. "ИИ-описания
     тикетов")
   - `CRON_SECRET`, `AGENT_TELEGRAM_IDS`, `REPORT_TARGET_CHAT_ID` —
     опционально, для вечерней сводки в Telegram (см. "Вечерняя сводка и
     управление статусами через Telegram" ниже)
   - `PLATFORM_API_URL`, `PLATFORM_SERVICE_USERNAME`,
     `PLATFORM_SERVICE_PASSWORD` — опционально, включают инструмент смены
     почты ученику (см. "Смена почты ученику" ниже); без всех трёх страница
     и пункт меню "Почта" скрыты
   - `LOGS_SERVICE_URL`, `LOGS_SERVICE_TOKEN` — опционально, включают поиск по
     логам Elasticsearch (см. "Логи ученика" ниже); без обоих страница и
     пункт меню "Логи" скрыты. Адрес и токен — от уже задеплоенного сервиса
     `juz40-vpn-logs`
   - `VPN_VM_HOST`, `VPN_VM_USER`, `VPN_VM_SSH_KEY_B64` — опционально, дают
     кнопке включения/выключения VPN-сервиса управлять им по SSH (см. там
     же). `VPN_VM_SSH_KEY_B64` — приватный SSH-ключ к VM, закодированный в
     base64 (`base64 -i путь/к/ключу.pem`), т.к. Vercel хуже работает с
     многострочными значениями
4. Задеплой проект. Миграции и сид (дефолтные группы) прогоняются
   автоматически при каждой сборке — вручную ничего гонять не нужно (см.
   `package.json` → `build`).
5. Готово — сайт доступен по ссылке от Vercel. На логине выбираешь свой
   профиль (Ерош / Алпа / Дежурный) и вводишь свой пароль — авторство тикетов теперь
   проставляется автоматически по тому, кто залогинен, а не выбирается
   руками.

## Настройка Telegram-бота ("Входящие")

Бот сам читает сообщения в support-группах и присылает их на сайт во
"Входящие" (`/inbox`) — можно смотреть переписку и создавать тикеты, не
открывая Telegram.

### 1. Создать бота

1. Напиши [@BotFather](https://t.me/BotFather) в Telegram → `/newbot` →
   придумай имя и username → получишь **токен** вида `123456:ABC-DEF...`.
2. Вставь токен в `TELEGRAM_BOT_TOKEN` (локально в `.env`, на Vercel — в
   Environment Variables).

### 2. Разрешить боту видеть все сообщения

По умолчанию бот видит только команды. Нужно отключить privacy mode:

1. Напиши @BotFather → `/setprivacy` → выбери своего бота → **Disable**.
2. Добавь бота как обычного участника во все 4 группы (админ-права не
   нужны).

### 3. Зарегистрировать вебхук (после деплоя на Vercel)

Telegram должен слать сообщения на публичный HTTPS-адрес — то есть это
делается **после** первого деплоя, когда есть домен от Vercel.

```bash
curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
  -d "url=https://<твой-домен>.vercel.app/api/telegram/webhook" \
  -d "secret_token=<TELEGRAM_WEBHOOK_SECRET>"
```

Значения `<TELEGRAM_BOT_TOKEN>` и `<TELEGRAM_WEBHOOK_SECRET>` — те же, что
ты положил в переменные окружения на Vercel. Ответ `{"ok":true,...}`
означает, что всё подключилось.

Проверить текущий статус вебхука можно так:

```bash
curl "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/getWebhookInfo"
```

### 4. Зарегистрировать команды бота (необязательно, но удобно)

Команды (`/report`, `/send`, ...) работают и без этого шага — бот видит
любое сообщение личке независимо от того, знает ли о нём Telegram. Этот
вызов только добавляет автодополнение: начинаешь печатать "/" в чате с
ботом — Telegram сам показывает список с подсказками.

```bash
curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setMyCommands" \
  -H "Content-Type: application/json" \
  -d '{
    "commands": [
      {"command": "report", "description": "Актуальный репорт за сегодня"},
      {"command": "send", "description": "Отправить репорт в группу"},
      {"command": "dedupe", "description": "Найти и объединить похожие тикеты"},
      {"command": "review", "description": "Начать разбор тикетов по одному"},
      {"command": "autoreply", "description": "Автоответы бота в группах: on / off"},
      {"command": "readchat", "description": "Статусы по моим ответам: on / off"},
      {"command": "broadcast", "description": "Объявление во все рабочие группы"},
      {"command": "help", "description": "Список команд"}
    ]
  }'
```

### 5. Как это работает дальше

- Каждое новое сообщение из группы попадает во "Входящие" на сайте.
- Если сайт ещё не знает, какой группе принадлежит чат — покажет жёлтый
  селектор "выбери группу". Выбираешь один раз — дальше все сообщения из
  этого чата будут подтягиваться в нужную группу автоматически.
- Ошибся с привязкой? У каждой уже привязанной группы (вкладка
  "Сообщения" во "Входящих") рядом с фильтром есть маленькая кнопка
  сброса — снимает привязку только у **этой одной** группы. Раньше кнопка
  была одна на все 4 группы и сбрасывала их разом — легко было случайно
  снести рабочие привязки остальных, пытаясь починить одну.
- На каждое сообщение — кнопка **"Создать тикет"** (описание и ссылка на
  сообщение подставляются автоматически) или **"Скрыть"**, если тикет не
  нужен.

### 6. Свои сообщения не попадают во "Входящие"

Ответы, которые Ерош и Алпа пишут прямо в группе (не через сайт), не должны
попадать во "Входящие" — это не запросы пользователей. Фильтрация идёт по
числовому Telegram id (не по имени — имя может отображаться по-разному, id
не меняется):

1. Напиши боту [@userinfobot](https://t.me/userinfobot) → `/start` — он
   пришлёт твой числовой `Id`.
2. Пусть второй агент сделает то же самое.
3. Впиши оба id через запятую в `OWN_AGENT_TELEGRAM_IDS` (локально в `.env`,
   на Vercel — в Environment Variables) и передеплой.

Своё сообщение всё равно **сохраняется** в базе (`TelegramMessage`, сразу
`archived`/`viewed`) — тикет из него не заводится, но если позже кто-то
ответит на него реплаем (например, попросит фидбэк по объявлению), это
уже обычный реплай на существующее сообщение: заведётся новый тикет с
цитатой контекста, как описано в ["Ответы на чужие
сообщения"](#ответы-reply-на-чужие-сообщения). До этой правки такие
сообщения не сохранялись вообще, и реплай на них терялся молча — ни в
тикет, ни во "Входящие".

## Как это устроено

- **Группы** (`GroupPreset`) — 4 дефолтные телеграм-группы (Әдістеме & IT,
  Сату - Платформа, IT & Product, IT + Сервис) с фиксированным порядком.
  Можно на лету добавлять произвольные группы (например, "Жеке чат: Имя") —
  они попадут в конец репорта.
- **Тикеты** (`Issue`) привязаны к дате репорта (`reportDate`, формат
  `YYYY-MM-DD`), группе, статусу (`SENT` / `IN_PROGRESS` / `PENDING` /
  `ESCALATED` / `RESOLVED`), с полями для Telegram-ссылки, заметки и ссылки
  на тикет (Jira/Atlassian), плюс автор и таймстемпы — это и есть базовое
  логирование. Автор проставляется сервером по сессии (кто залогинен), а не
  выбирается вручную в форме. Новый тикет по умолчанию создаётся со
  статусом `SENT` ("Отправлено") — это стартовая точка, работа с ним ещё не
  начата.
- **Передано другой команде** (`ESCALATED`) — третья кнопка внутри колонки
  "В работе / Пендинг" (и на доске, и в форме редактирования), рядом с "В
  работе"/"Пендинг". В отличие от них требует деталей — открывает
  `EscalateDialog`: команда (`Issue.escalatedTeam`, фиксированный список в
  `src/lib/escalation.ts` — сейчас Backend/Frontend/Product/Мобайл) и
  необязательно кто занимается (`escalatedAssignee`). Заметка по умолчанию
  синхронизируется с выбором ("Передано: Backend (Аян)") и попадает в
  репорт как обычно. Если такой тикет потом переводят в "Решено" —
  `ResolveDialog` подставляет дефолт заметки `"<команда> шешті"` вместо
  `"<агент> шешті"`: закрыл карточку саппорт-агент, но решала не он.
- **Реакция бота в Telegram по статусу.** При смене статуса тикета (в
  любом месте — доска, форма, кнопка "Решено") бот ставит реакцию на
  исходное сообщение в чате: 👀 для "В работе"/"Пендинг"/"Передано", 👍 для
  "Решено" (у Telegram нет ✅ среди разрешённых emoji-реакций для ботов —
  `ReactionTypeEmoji`), для "Отправлено" реакция не ставится (и снимается,
  если тикет вернули в этот статус). Реализовано через
  `setMessageReaction` в `src/lib/telegram.ts`, вызывается из `PATCH
  /api/issues/[id]` по совпадению `Issue.telegramLink` с `messageLink`
  сохранённого `TelegramMessage` (chatId + messageId для вызова Bot API).
  Ошибки Telegram (нет прав на реакции в чате, сообщение удалено и т.п.)
  намеренно проглатываются — это бонус к статусу, а не часть его
  сохранения, ронять обновление тикета из-за них не нужно.
- **Генератор репорта** (`src/lib/report.ts`) собирает текст в формате,
  который раньше писали руками: группы по порядку, нумерация с 1 в каждой
  группе, ✅/⚠️ по статусу, разделитель между группами. Тикеты со статусом
  `SENT` ("Отправлено") в текст репорта не попадают — по ним ещё ничего не
  происходило, рано выносить в отчёт; как только статус меняется на
  `IN_PROGRESS`/`PENDING`/`RESOLVED`, тикет появляется в репорте.
- **Главная страница** (`/`) — рабочий стол на любую дату (по умолчанию
  сегодня, можно листать стрелками или выбрать дату) со списком тикетов по
  группам (включая "Отправлено" — здесь видно всё, фильтр только для
  текста репорта): ручная сортировка (стрелки), редактирование и удаление,
  живой предпросмотр готового текста репорта и кнопка "Скопировать".
- **История** (`/history`) — список всех дней, по клику открывается тот же
  рабочий стол на нужную дату.
- **Входящие** (`/inbox`) — рабочее место для разбора дня, с переключателем
  **Сообщения / Доска** (по умолчанию открывается **Доска**):
  - **Доска** — канбан на весь экран, в 3 колонки: "Отправлено" / "В работе
    и Пендинг" (статусы `IN_PROGRESS` и `PENDING` объединены — это один
    рабочий процесс, переключаются парой кнопок внутри карточки) / "Решено".
    Тикет перетаскивается между колонками мышкой — статус меняется сразу.
    Исключение — перевод в "Решено": он сначала открывает модалку **"Как
    решили?"** с заметкой (по умолчанию "Имя шешті", можно дописать), и
    только после подтверждения статус применяется. Заметка идёт прямо в
    текст репорта, а если не спросить её в момент закрытия, к вечеру уже
    никто не помнит, чем всё кончилось. Отмена в модалке оставляет тикет
    там же, где он был.
    Как только сообщение приходит из чата, у которого группа уже известна
    (chatId раньше привязали к одной из 4 групп), вебхук (`/api/telegram/webhook`)
    **сразу заводит тикет сам** со статусом "Отправлено" — руками "Создать
    тикет" нажимать не нужно, оно просто появляется на доске. Описание при
    этом чистится автоматически (`src/lib/textClean.ts`): убираются
    казахские/русские приветствия ("Қайырлы күн", "Сәлеметсіз бе",
    "Здравствуйте" и т.п.), голые ссылки (и подпись "Ссылка:"), почта и
    номер телефона (в любом написании, например "Почта: ..." / "Номер:
    ..." снизу), плейсхолдеры вложений ("[Фото]", "[Видео]" и т.п.), а
    также строки с логином/паролем ("логин\nBalausa10\nпароль\n...") — то,
    что раньше всегда вырезали руками. Тот же вызов чистки срабатывает и при
    ручном редактировании/создании тикета агентом (`PATCH`/`POST
    /api/issues`), не только при авто-создании ботом — иначе приветствие, не
    убравшееся при заводе тикета, оставалось бы висеть навсегда. Если после
    чистки от сообщения не остаётся ничего по делу (голое "Қайырлы күн",
    одна ссылка, "[Фото]" без подписи, "рахмет 👍", а также **одни только
    учётные данные** — номер, почта, логин, пароль без единого слова о
    проблеме: это данные, которые сам же агент и попросил для проверки уже
    известного обращения) — **тикет не заводится
    вообще** (`isNoiseOnly` в `src/lib/textClean.ts`), чтобы не забивать
    доску карточками, по которым нечего делать; само сообщение при этом
    остаётся во "Входящих" с кнопкой "Создать тикет". Частый порядок
    "приветствие отдельным сообщением, проблема следующим" при этом не
    ломается: когда второе сообщение приклеивается к первому (окно 5 минут),
    тикет заводится уже по склеенному тексту. Тоглом
    **"✨ ИИ-описания"** в шапке `/inbox` эта regex-чистка входящих сообщений
    заменяется переписыванием через ИИ (Groq) — см. "ИИ-описания тикетов"
    ниже. Автором такого тикета сначала стоит
    "Бот" — как только с ним
    что-то делает живой агент (меняет статус, редактирует), авторство сразу
    переходит на него (см. `PATCH /api/issues/[id]`). Если следом приходит
    ещё сообщение от того же человека в течение 5 минут (та же склейка, что
    и в ленте) — текст дописывается и в привязанный тикет тоже (тоже через
    чистку). Для чатов, которым ещё не назначили группу, авто-создание не
    работает (группа обязательна для тикета) — там по-прежнему нужно один
    раз выбрать группу и нажать "Создать тикет" вручную. На каждой карточке
    — ссылка "Открыть в Telegram" на исходное сообщение, иконка
    редактирования (открывает ту же форму тикета, что и на главной
    странице) и иконка удаления. Если за день остались тикеты со статусом
    `PENDING` (старый дефолт до перехода на `SENT`, то есть статус никто
    явно не выставлял) — появляется кнопка **"Пендинг без статуса →
    Отправлено"**, разово переносящая их в нужную колонку
    (`POST /api/issues/normalize-status`). Если среди тикетов "Отправлено"
    есть такие, что завелись ещё до появления автоочистки описаний (со
    ссылками/приветствиями/логинами внутри), появляется кнопка **"Почистить
    описания в «Отправлено»"** — разово прогоняет их через
    `cleanTicketDescription` (`POST /api/issues/clean-descriptions`).
  - **Сообщения** — лента сообщений из Telegram (`TelegramMessage`),
    которые пришли через вебхук бота (`/api/telegram/webhook`), с фильтром
    по группе (пилюли "Все" / название группы / "Без группы"). Для чата с
    уже известной группой тикет уже заведён автоматически — вместо кнопки
    "Создать тикет" показывается кнопка **"Тикет заведён автоматически —
    изменить"**, которая открывает ту же форму редактирования, что и на
    доске, прямо здесь, без переключения вкладки. Для остальных — можно
    превратить сообщение в тикет вручную (одной кнопкой, с автоподстановкой
    уже очищенного описания и ссылки) или скрыть. Привязка chat_id →
    группа запоминается в `GroupPreset.chatId` после первого ручного
    выбора.

## Интерфейс: поиск, горячие клавиши, модалки

- **Командная палитра** (`⌘K` / `Ctrl+K`, компонент
  `src/components/CommandPalette.tsx`) — один вход и в поиск по тикетам
  дня (по описанию, группе и заметке), и в действия страницы. На доске за
  активный день набирается несколько десятков карточек в трёх колонках, и
  найти нужную глазами дольше, чем набрать пару букв. Найденный тикет
  открывается на редактирование и подсвечивается кольцом на доске, чтобы
  после закрытия было видно, где он лежит. Кнопка «Поиск ⌘K» в шапке
  показывается только на `/` и `/inbox` — на «Истории» палитры нет,
  потому что ей нужен список тикетов за день.
- **Горячие клавиши** (`src/lib/useHotkeys.ts`) — `←`/`→` листают дни,
  `t` возвращает на сегодня, `?` показывает полный список. На дашборде
  дополнительно `n` (новый тикет) и `c` (скопировать репорт), во
  «Входящих» — `b`/`m` (Доска/Сообщения) и `f` (фокус в фильтр). Хук сам
  не срабатывает, когда фокус в поле ввода или открыта модалка, — иначе
  «н» в описании тикета открывало бы новую форму.
- **Фильтр на доске** — сужает карточки по тексту, не перезагружая
  данные; рядом видно «сколько из скольких» осталось.
- **Модалки** (`src/components/Modal.tsx`) — общая обёртка для всех окон.
  Раньше каждое окно городило свой оверлей и одинаково не умело трёх
  вещей: удерживать `Tab` внутри себя, не давать фону прокручиваться под
  собой и возвращать фокус туда, откуда его открыли.
- **Тосты и подтверждения** вместо `window.alert`/`window.confirm`
  (`src/components/Toast.tsx`, `ConfirmDialog.tsx`). Нативные окна рвали
  визуальный контекст и, что важнее, показывали «Удалить тикет» и
  «Перевести пендинги» совершенно одинаково — теперь опасное действие
  красное и в нём видно текст самого тикета.
- **Мобильная доска** — три колонки по 60vh на телефоне превращались в
  простыню на три экрана; вместо этого колонки переключаются табами.
- Анимации появления и `prefers-reduced-motion` — в `globals.css`.
  Системная настройка «меньше движения» выключает их полностью, а не
  замедляет.

## Ответы (Reply) на чужие сообщения

Сообщение-ответ ("Reply" в Telegram) само по себе часто нечитаемо: "Әдістеме
бөлінді нұсқа салынып тұр дейді" ("дейді" — "говорят") ничего не значит,
если не видно вопроса, на который отвечали. Раньше вебхук брал только текст
самого ответа — вопрос, на который отвечали, терялся, и regex/ИИ строили
описание по обрывку.

Теперь, если сообщение — ответ на другое (`reply_to_message` в апдейте от
Telegram), вебхук приклеивает цитату первой строкой: `↩️ Автор: текст
вопроса`, и уже с ней сохраняет сообщение (`extractReplyContextLine` в
`src/lib/telegram.ts`). Эта строка:

- **видна во "Входящих"** — в ленте сообщений и в источнике для кнопки "ИИ
  написал не то?" (`raw-source`), не только в момент создания тикета;
- **идёт в контекст для regex/ИИ**, когда решаем, каким должно быть
  описание — ИИ вплетает контекст в связный текст и не копирует саму строку
  `↩️ ...` в результат (см. промпт в `src/lib/ai.ts`). При выключенном ИИ
  (или если запрос к нему упал) строку `↩️ Автор: ...` из финального
  описания вырезает уже сама regex-чистка (`REPLY_QUOTE_LINE` в
  `src/lib/textClean.ts`) — раньше она про этот формат ничего не знала, и
  цитата навсегда оседала в описании тикета вместо сути обращения;
- **не участвует в проверке на мусор** (`isNoiseOnly`) — решает только то,
  что человек буквально написал сам: голое "ок" в ответ на чужой вопрос всё
  равно не тикет, вне зависимости от того, что за вопрос был.

## Напоминания: ответ на уже заведённое сообщение

Частый паттерн: человек отвечает (Telegram Reply) на своё же старое
сообщение, на которое так и не отреагировали — "Осы бойынша кері байланыс
бере аласыздарма?" ("Можете дать обратную связь по этому?"). Сама по себе
такая реплика не тикет и не имеет смысла без исходного вопроса — а если
исходный тикет уже (ошибочно) закрыт как "Решено", то это ещё и сигнал,
что закрыли зря.

Вебхук ищет по точному `reply_to_message.message_id`, заведён ли уже тикет
на то сообщение (`attachFollowUpToTicket` в `src/app/api/telegram/webhook/route.ts`).
Если да — вместо нового, оторванного от контекста тикета:

- новое сообщение приклеивается ссылкой к найденному тикету (тот же
  механизм, что у `extraLinks`/`attach-message`);
- если тикет был **"Решено"** — статус возвращается в **"Отправлено"**, а
  в заметку дописывается `"жауап берілмеді, қайта хабарласты"` — не
  затирая прежнюю заметку, а строкой поверх (`"Ерош шешті → жауап
  берілмеді, қайта хабарласты"`), чтобы была видна вся история;
- если тикет ещё не решён (`SENT`/`IN_PROGRESS`/`PENDING`) — статус не
  трогаем, просто добавляем ссылку: агент и так знает, что не ответил.

Мусорные ответы ("рахмет", "ок" в ответ на своё старое сообщение) это не
триггерит — проверяется собственный текст реплики, тот же `isNoiseOnly`,
что и везде.

## Повторы: несколько обращений в одном тикете

Один и тот же запрос часто прилетает по нескольку раз ("доступ беріңізші"
от трёх разных мұғалім-ов) — это один тикет с несколькими ссылками, а не
три карточки на доске. Объединение всегда делает человек, автоматического
склеивания нет (см. ниже почему).

Два сценария, оба в `/inbox`:

- **Тикеты уже завелись** (чат привязан к группе, поэтому вебхук завёл
  тикет на каждое сообщение) — на карточке дубля жми иконку 🔗 → выбери,
  в какой тикет объединить. Дубль исчезает, его ссылки переезжают в
  выбранный тикет (`POST /api/issues/[id]/merge-into`).
- **Сообщение ещё не разобрано** (чат без группы) — на карточке сообщения
  во вкладке "Сообщения" кнопка **"К существующему"** рядом с "Создать
  тикет" (`POST /api/issues/[id]/attach-message`).

В обоих случаях список тикетов отсортирован **по похожести** на текст
(`src/lib/similarity.ts`, пересечение слов — считается на клиенте,
бесплатно), подходящие помечены синим бейджем "похоже", так что нужный
обычно оказывается первым. Промахнулись — и на дашборде, и на доске
"Входящих" рядом с приклеенной ссылкой есть ✕: она отвязывается, а
сообщение возвращается во "Входящие" неразобранным (`DELETE
/api/issues/[id]/attach-message`).

Похожесть текста ловит "тот же тип проблемы", а не "тот же ученик" — куратор,
который ведёт нескольких учеников, часто присылает про второго ученика
теми же словами ("+тағы бір оқушы"), и такое сообщение тоже помечается
"похоже", хотя случай другой. Если у сообщения и у кандидата известна почта
(`hints.emails`, см. ниже) и они разные, рядом появляется жёлтый бейдж
"⚠️ другая почта" — это тоже только подсказка, объединять или нет всё равно
решает агент.

В репорте все ссылки идут отдельными строками под одним пунктом:

```
1. Деңгейлік тестке доступ беріңізші
https://t.me/c/555000222/700001
https://t.me/c/555000222/700002
https://t.me/c/555000222/700003
Статус: Ерош шешті, доступ берілді✅
```

**Почему объединение не автоматическое.** Похожие тексты — не гарантия
одного и того же запроса: "доступ беріңізші" от двух учителей вполне может
быть про двух разных учеников, и молча склеенные обращения означают
потерянный запрос, которого никто не хватится (репорт — это то, по чему
отчитываются). Поэтому похожесть считается и показывается, но решение
остаётся за агентом: цена ложного объединения выше, чем цена одного клика.
Схема при этом уже готова к нескольким сообщениям на тикет
(`TelegramMessage.usedForIssueId` — many-to-one, `Issue.extraLinks`).

**Список ссылок ≠ список сообщений (`ATTACH_LINK_POLICY`).** Это два разных
понятия, и путать их нельзя:

- **`Issue.extraLinks`** ("Ещё обращение №2" на карточке) — список РАЗНЫХ
  обращений по одной и той же проблеме: Али написал про пароль, потом Айжан
  написала про пароль — дежурному нужен один тикет с двумя ссылками, а не
  два тикета. Добавляется **только человеком** — кнопками "Прикрепить" /
  "Объединить" (`attach-message`, `mergeIssue.ts`): только агент знает, что
  это два разных ученика с общей причиной.
- **`TelegramMessage.usedForIssueId`** — "это сообщение относится к этому
  тикету". Ставится и автоматикой тоже: когда тот же человек по тому же
  случаю досылает уточнения (отвечает на вопрос бота, дописывает подробности,
  реплаит сам себе).

Раньше автоматические пути добавляли ссылку на каждое уточнение, и карточка
одного обращения обрастала списком "Ещё обращение №2..№6", в котором ни одна
ссылка не вела к формулировке проблемы. Теперь автоматика ставит только
привязку и не трогает `extraLinks` — на карточке остаётся ссылка на
сообщение с реальной проблемой. Зацепки при этом не теряются: почта,
телефон и факт вложения собираются именно по `usedForIssueId` (см. `hints` в
`api/issues` и `hintsFor` в `lib/dailyReview.ts`), поэтому присланная почта
по-прежнему видна на карточке — просто без лишней ссылки рядом.

## Тикет по ссылке, которой нет во "Входящих"

Кнопка **"+ Новый тикет"** на доске "Входящих" (горячая клавиша `n`) — для
случая, когда ссылку на Telegram-сообщение прислали не туда, куда смотрит
бот (личка, чат без бота, пересланный скриншот с текстом ссылки) — то есть
самого сообщения во "Входящих" нет и не будет, заводить не от чего. Открывает
ту же форму тикета, что и везде (`IssueForm`, с выбором группы), поле
"Ссылка на Telegram-сообщение" — просто текстовое поле, можно вставить
любую ссылку руками. Ничего не заводится автоматически по одной ссылке —
как и с обычным ручным тикетом, описание тоже пишет агент.

## Автоответы бота в рабочие группы

Единственная фича, которая пишет от имени школы туда, где сидят коллеги
(сервис, сату, әдістеме, продукт), поэтому **по умолчанию выключена**.
Включается тумблером **"🤖 Автоответы"** во "Входящих" (включение
спрашивает подтверждение, выключение — нет: выключить всегда должно быть
легко) или командой `/autoreply on|off` в личке с ботом; без аргумента
команда покажет текущее состояние и что именно бот делает.

Формулировки (`src/lib/autoReply.ts`) взяты из настоящей переписки Ероша и
Алпы, а не придуманы — бот должен звучать как коллега, а не как система.
В частности "кб" (кері байланыс) намеренно оставлено сокращением: именно
так пишут в этих чатах. Приветствие подставляется по времени суток
(«Қайырлы күн» / «Қайырлы кеш») — пятая часть обращений приходит после
18:00, и бот, желающий доброго дня в 23:00, сразу выдаёт в себе робота.
Утреннего «Қайырлы таң» намеренно нет: в выгрузке рабочих групп до полудня
агенты пишут «Қайырлы күн» 775 раз против 40 — форма правильная, но в этих
чатах ей не пользуются.
Язык ответа выбирается по языку обращения: казахские буквы (ә, ғ, қ, ң, ө,
ұ, ү, і) есть — отвечаем по-казахски, только русская кириллица — по-русски.

### Сначала спрашивает, потом пишет

Тумблер **"🙋 Спрашивать перед ответом"** (включён по умолчанию, работает
поверх автоответов). Пришло обращение — в группу не уходит ничего; вместо
этого дежурному в личку приходит черновик:

```
🤖 Ответить в «Сату - Платформа»?

Обращение: Нұржан Нұрдаулет, пән ауыстыру керек, джт орнына география

1) Қайырлы күн, жақсы, ауыстырылғанда кб береміз. Тексеру үшін оқушының аты-жөнін жібере аласыз ба?
2) Қайырлы күн, жақсы, ауыстырылғанда кб береміз
3) Қайырлы күн, жақсы, қарап кб беретін боламыз

Свой текст — ответь реплаем на это сообщение.
   [✅ 1] [✅ 2] [✅ 3]
   [🚫 Не отвечать]
```

Варианты отличаются не формулировкой, а решением — просить данные или нет.
Именно здесь бот ошибается чаще всего, и нажатием это исправить дешевле,
чем набирая текст. Реплай своим текстом отправляет в группу ровно его.

Смысл режима в том, что он снимает главное возражение против автоответов:
включённый бот больше не может ничего испортить, потому что сам он ничего
не отправляет — худшее, что бывает, это неотправленный черновик. Если
никто не нажмёт, в группу не уйдёт ничего.

**Когда про одно и то же пишут несколько человек.** В 16:09 методист
пишет «квал тесттер мүлдем шықпайды», в 16:11 второй — «менде КВАЛЛ тамыз
2026 - куратор деген курс жоқ», в 16:13 третий про то же. Это одна
поломка, а не три задачи. Если за последние 30 минут в этом чате уже есть
похожее обращение от **другого** человека, в черновике появляется
четвёртая кнопка:

```
🔗 Похоже на то, что писал(а) Азамат 2 мин назад:
«Менің аккаунтымды қарап жібере аласыздар ма? Квал тесттер шықпайды»
   [🔗 Это то же самое — ответить всем разом]
```

Нажатие делает то же, что «объединить» на сайте: ссылки съезжаются в один
тикет, сообщения перецепляются туда же, лишний тикет исчезает — и в группу
уходит **одно** сообщение вместо трёх одинаковых: «жақсы, бұл мәселе
бойынша қарап жатырмыз — шешілгенде осында хабарлаймыз». Оно ничего не
просит: данные тут ничего не решают, сломано у всех.

Похожесть считается по основам слов (`stemSimilarity`), а не по словам
целиком: казахский агглютинативный, и у трёх человек про одну поломку
общих слов почти нет. Порог низкий намеренно — кандидат только
предлагается кнопкой. Автоматически склеивать нельзя: обращения в этих
чатах устроены однообразно («имя, почта, ссылка керек»), и пять разных
заявок подряд выглядят похоже, не будучи одним случаем. По выгрузке такой
кандидат находится примерно у 7 % обращений.

Пока черновик ждёт, коллега может ответить в группе сам — тогда нажатие
уже ничего не отправит: правило «бот пишет только то, чего там ещё не
прозвучало» проверяется ещё раз в момент нажатия, а не только при
создании черновика.

Реакции на смену статуса подтверждения не требуют: их вызывает осознанное
действие человека, переспрашивать не о чем.

**Что бот пишет сам:**

- **Подтверждение приёма** — сразу, как по сообщению завёлся тикет.
  Отправляется, только если тикет реально создан, поэтому мусор
  («рахмет», стикеры) ответа не порождает — фильтр достаётся от
  `isNoiseOnly` бесплатно.

  Без ИИ ответ общий: «Қайырлы күн, жақсы, қарап кб беретін боламыз», плюс
  просьба прислать почту или ссылку, если regex не нашёл в тексте ни
  почты, ни ссылки, ни номера.

  Тумблер **"🎯 Отвечать по ситуации"** (выключен по умолчанию,
  работает только поверх уже включённых автоответов) заменяет это разбором
  по **каталогу ситуаций** — `src/lib/situations.ts` плюс
  `classifySituation` в `src/lib/ai.ts`. Модель определяет две вещи: что за
  случай (17 ситуаций: правка задания, оплатил-нет-доступа, смена предмета,
  кабинет родителя, предложение функции, возврат…) и чего в сообщении не
  хватает. Слова ответа она не выбирает — обещание и формулировку просьбы
  берёт код.

  Отсюда две вещи, которых раньше не было:

  - **Обещание зеркалит просьбу.** На правку контента — «өзгертілгенде кб
    беретін боламыз», на доступ — «ашылғанда кб береміз», на смену данных —
    «ауыстырылғанда кб береміз», на предложение функции — «Ұсыныс үшін
    рақмет, ойланып көреміз» вместо обещания что-то починить.
  - **Просят ровно то, чего не хватает**, а не почту по умолчанию: аты-жөні
    (в отделе продаж ученика ищут по имени, по одной почте не находят),
    ай-апту, аккаунт, оба номера сразу для кабинета родителя. И чаще всего
    не просят ничего: по выгрузке четырёх групп живой агент просит данные
    лишь в 22 % обращений без идентификатора, а regex-версия просила почти
    всегда.

  Две ситуации отвечают по существу вместо обещания, потому что ответ
  известен заранее: `parent_email_clash` (почта ученика и родителя
  совпадают — регистрация и не могла пройти) и `mobile_app` (проверьте
  версию приложения).

  При недоступности модели — откат на прежний общий ACK: не суметь
  разобрать обращение не значит промолчать.
- **Реакция на смену статуса** — «Жұмысқа алдық» / «Қарап жатырмыз» /
  «Әріптестеріме жібердім», когда статус меняют **на сайте или в разборе**.
  Отключается отдельным тумблером **"💬 Писать при смене статуса"**: это
  первое, что начинает надоедать, если тикет за день двигают несколько раз.
  Эмодзи-реакция на исходном сообщении остаётся в любом случае — она видна
  только там и никого не отвлекает.

  **Два движения подряд — одно сообщение.** Статус часто меняют в два
  шага: карточку кладут в «В работе», а через несколько секунд жмут
  «Передано»; или роняют не в ту колонку и тут же тащат обратно. В проде
  таких пар за неделю набралось больше десятка, и каждая давала в чате два
  сообщения бота подряд про один тикет. Теперь свежий (моложе 5 минут)
  ответ про статус не дублируется, а **переписывается** — в группе остаётся
  одно сообщение, показывающее текущее положение дел. А если тикет
  вернулся в «Отправлено» сразу после «В работе» — значит промахнулись
  колонкой, и сообщение просто удаляется: извиняться за задержку не за что.

  **У объединённого тикета ответ один и без цитаты.** Если в тикет слиты
  обращения нескольких человек (`extraLinks` непустой), реплаем отвечать
  нельзя — цитата выделит одного, а написали все. Бот шлёт одно сообщение
  без цитаты, а чтобы «жұмысқа алдық» не повисло в чате ни к чему не
  привязанным, ИИ добавляет название темы: «Квал тест — жұмысқа алдық,
  қарап жатырмыз» (`summarizeIssueTopic`; модель недоступна — остаётся
  просто «Жұмысқа алдық, қарап жатырмыз»).
- **Ответ на повторное обращение** по уже «решённому» тикету —
  «Кешіріңіз, кідіріп қалды». Человек пишет второй раз именно потому, что
  ему не ответили, и молчание тут и есть сама проблема. Этот путь
  (`attachFollowUpToTicket`) меняет статус в обход `reactToStatusChange`,
  поэтому ответ там отправляется явно.

**Что бот НЕ пишет сам** — «Решено». Это единственный ответ, который
утверждает факт, а не обещает внимание: если статус проставили ошибочно,
коллега узнаёт от бота, что задача закрыта, хотя это не так. Поэтому после
сохранения заметки о решении в разборе появляется кнопка **"💬 Сообщить в
чат, что решено"**, и только по ней уходит «Жөнделді» или «Өзгертілді» —
слово выбирает ИИ по сути тикета (`pickResolvedWord` в `src/lib/ai.ts`:
чинили поломку → «Жөнделді», меняли данные по просьбе → «Өзгертілді»;
при недоступности модели — «Жөнделді», отправку это не блокирует).

### Когда тикет не заводится

Ответ (Reply) на сообщение нашего же агента и реплай самому себе тикета не
создают: это продолжение разговора, а не новое обращение. Решение
запоминается на самом сообщении (`TelegramMessage.skippedAutoIssue`), и это
не деталь реализации, а суть — **пропуск наследуется всей склеенной
серией**.

Без этого он жил ровно одно сообщение. В проде это видно поимённо: человек
отвечает реплаем нашему агенту (тикет не заводится, правильно), через две
секунды дописывает следующей фразой — и она заводит тикет, причём вместе с
процитированным текстом агента в описании. Так появились четыре тикета,
включая ответ Алпе на его же разбор. Теперь в серии достаточно одного
пропуска, чтобы не завелось ничего, сколько бы фраз человек ни дописал.

### Обратная связь: из чата в статус

Связь работает и в другую сторону — иначе автоответы стали бы третьим
местом, где надо отмечаться. Дежурный отвечает в группе как привык, а
`detectAgentIntent` (`src/lib/agentIntent.ts`) распознаёт по его реплике,
что произошло, и двигает статус сам:

| Что агент написал | Что делает система |
| --- | --- |
| «Жақсы, тексеріп береміз» | `IN_PROGRESS`, молча |
| «Әріптестеріме жібердім» | `ESCALATED`, молча |
| «Жөнделді», «ауыстырылды, жіберілді», «өшірілді» | спрашивает в личке — с уже готовой заметкой |

Правилами, а не ИИ: на разборе реальной недельной переписки те же признаки
уверенно опознали половину ответов, стоят ноль и не зависят от внешнего
сервиса. Что не опознали — просто остаётся человеку, это не ошибка.
Будущее время исключено намеренно: «бүгін шешіледі» — обещание, а не факт.
Слова готовности сверены с выгрузкой четырёх групп и упорядочены по
частоте: `ауыстырылды` 469, `жіберілді` 408, `қосылды` 200, `шешілді` 199,
`ашылды` 150, `жөнделді` 114, `өзгертілді` 101, `өшірілді` 97,
`дұрысталды` 69, `түзелді` 38.

**К какому тикету относится реплика** (`resolveAgentTarget` в
`src/lib/agentThread.ts`). Стрелка Reply закрывает 90 % случаев: из 1 316
реплик о готовности в выгрузке 1 189 отвечают на конкретное сообщение.
Оставшиеся 10 % раньше пропадали — тикет брался, только если в чате за
день открыт ровно один, а в Сервисе и Сату их всегда несколько. Порядок
поиска теперь такой:

1. **Стрелка Reply** — как и раньше, самый точный признак.
2. **Свой же разговор** — последняя собственная реплика, про которую уже
   известно, о каком она тикете. Это случай «Окей, қазір» в 18:34 →
   «өшірілді» в 18:38: второе сообщение продолжает первое (59 случаев из
   127). Не срабатывает, если между ними пришло новое обращение — тогда
   моя фраза с тем же успехом отвечает ему.
3. **Ближайшее обращение выше** — так же, как читает человек, открывший
   чат (68 случаев из 127). Окно 30 минут: когда клиент в чате один,
   разрыв до его сообщения — медиана 4,5 минуты, 90-й перцентиль 19.

Если после всего этого кандидатов несколько (35 % реплик без стрелки —
в чате за полчаса писал не один человек), система по-прежнему не гадает,
но и не молчит, как раньше: присылает в личку вопрос «к какому тикету это
относится?» с кнопками на 2–3 последних обращения. Одно нажатие вместо
ручного проставления статуса вечером. Ошибиться статусом хуже, чем
переспросить: он уходит в репорт боссам.

**Закрытие в одно нажатие.** Вопрос «похоже, решён — отметить?» приходит с
уже собранной заметкой из собственных слов агента в чате
(`summarizeResolutionNote`, та же машинерия, что в модалке «Как решили?» на
сайте): «✅ Решено, с этой заметкой» — и всё, ничего набирать не нужно.
Вторая кнопка «✍️ Написать свою» ведёт в прежний путь с ответом реплаем.
Текст при нажатии читается из самого сообщения, а не пересчитывается
моделью заново: человек соглашается с конкретной формулировкой, и закрывать
тикет чем-то другим нельзя.

Это не украшение, а противовес перекосу. Статус выводится из реплик, а в
чате о начале работы говорят чаще, чем о конце: из 10 577 обращений, на
которые агент ответил, «қараймыз» звучит в 28 %, слово о готовности — в
31 %, и то и другое — лишь в 12 %. Оставшиеся 16 % («сказал, что смотрит,
и молча доделал») и оседали бы в колонке «В работе». Отличить вежливое
«принято» от «реально взял» по формулировке нельзя — все формы доводятся до
слова о готовности примерно одинаково часто (23–47 %), так что лечится не
вход, а выход: закрывать должно быть так же дёшево, как попадать.

Остаток ловится пометкой: тикет, который стоит в «В работе» или «Пендинг»
дольше 3 часов, получает на доске жёлтое «⏳ N ч», а вечерняя сводка —
строку «Висят в работе больше 3 ч: N — может, уже сделано?». Время считается
по `Issue.statusChangedAt`, а не по `updatedAt`: последний сдвигается от
любой правки текста, и счётчик обнулялся бы, когда статус не двигался.

### Одна точка входа для статуса

`changeIssueStatus` (`src/lib/issueStatus.ts`) — единственное место, где
статус меняется: сайт, кнопки разбора, реплики в группе, возврат решённого
тикета в работу. Она пишет статус, переоформляет автора с «Бота» на живого
агента, записывает событие в `IssueEvent` и зовёт `reactToStatusChange` с
нужным `source`. До неё эти четыре шага повторялись в восьми местах, а
забыть любой из них ничего заметно не ломало — просто где-то не появлялась
реакция, а где-то тикет навсегда оставался за ботом.

`IssueEvent` (`from`, `to`, `actor`, `source`, `at`) даёт то, чего раньше
нельзя было посчитать вообще: сколько времени проходит от обращения до
ответа и до решения, какая доля закрывается прямо из чата, а какая руками.

Связь «реплика → тикет» хранится в `TelegramMessage.agentIssueId` —
отдельно от `usedForIssueId` нарочно: там сообщения, ИЗ которых состоит
обращение (их текст идёт в описание и подсказки), здесь — то, что мы сами
сказали по нему.

**Правило, которое связывает оба направления:** бот пишет в группу только
то, чего там ещё не прозвучало. Технически это параметр `source` у
`reactToStatusChange` — `"app"` (сайт/разбор, в группе не знают → бот
пишет) или `"chat"` (статус изменился из-за реплики агента → бот молчит,
ставит только эмодзи-реакцию). Без него бот повторял бы за живым
человеком: тот написал «әріптестеріме жібердім», статус ушёл в «Передано»,
и бот следом пишет в ту же группу то же самое.

### Если бот ошибся

Всё отправленное записывается в `BotReply` (тикет, чат, `message_id`,
текст) — без этого неудачный ответ уже не достать. На карточке тикета на
доске под описанием видно, что бот сказал, с двумя действиями:

- **✎ Исправить** — вариант по умолчанию. Удаление ничего не исправляет
  для того, кто уже прочитал: если бот написал «Жөнделді» и человек на это
  среагировал, исчезнувшее сообщение оставит его в заблуждении. Правку он
  хотя бы увидит (Telegram пометит «изменено»), и тред с реплаем не рвётся.
- **✕ Удалить** — для случая, когда ответа вообще не должно было быть.

Оба работают только 48 часов — жёсткий лимит Telegram; дальше сервер
возвращает понятное «прошло больше 48 часов, убери вручную», а не молчит.
Удалённые ответы помечаются, а не стираются из базы: иначе непонятно, было
ли вообще что-то отправлено.

Ответы бота видны и на карточке разбора в Telegram (строкой «🤖 бот уже
ответил: …») — чтобы вечером не написать коллегам второй раз то же самое.
Там же кнопка **«🤖 Ответы бота»** (появляется, только если боту есть что
убирать) — открывает список с кнопкой удаления у каждого сообщения.
Удалять надо уметь с телефона: дежурный сидит в Telegram, а не на сайте.

**Ответ на просьбу прислать данные.** Когда бот просит почту или ссылку, а
человек отвечает реплаем на его сообщение, этот ответ приклеивается к тому
же тикету (`attachReplyToBotMessage` в вебхуке). Отдельно от
`attachFollowUpToTicket` по двум причинам: ответы бота лежат в `BotReply`,
а не в `TelegramMessage`, и проверку на мусор тут делать нельзя — голая
почта для `isNoiseOnly` и есть мусор (после чистки не остаётся ничего),
хотя это ровно то, что мы просили. Ответ на наш вопрос — не запрос, и
мерить его меркой запроса неверно. Без этого присланная почта осталась бы
болтаться во "Входящих" отдельным сообщением, не привязанным ни к чему.
Ссылку на карточку такой ответ не добавляет — только привязку, из которой
берётся сама почта (см. `ATTACH_LINK_POLICY` выше).

**Защита от дубля:** один ACK на тикет (сообщения одного автора склеиваются
в пределах 5 минут, а вебхук может доставиться повторно) и молчание, если
по обращению уже успел ответить живой человек — собственные сообщения
агентов сохраняются, так что проверка есть на чём построить.

**У каждого сообщения серии — своя строка в базе, даже склеенного.** Когда
несколько сообщений одного автора сливаются в один тикет (окно 5 минут выше),
в базу обновлялась только строка ПЕРВОГО сообщения серии — у второго,
третьего и т.д. своей строки не заводилось вообще, их текст просто дописывался
в первую. Из-за этого Telegram-реплай именно на второе (не первое) сообщение
серии не находил, к чему приклеиться (`attachFollowUpToTicket` ищет по
точному `chatId`+`messageId`), и заводил отдельный, оторванный тикет вместо
того, чтобы приклеиться к уже существующему. Теперь у каждого сообщения
серии есть своя строка, указывающая на тот же тикет — реплай на любое из
них находится.

**Ответ на просьбу прислать данные — без Reply, спустя долгое время.**
`attachReplyToBotMessage` и склейка по 5-минутному окну ловят только два
случая: ответили реплаем, или прислали новое сообщение почти сразу же. Если
человек отвечает не реплаем, а просто новым сообщением через 10+ минут (типичная
задержка — надо найти почту/сделать скриншот), оно раньше заводило второй,
не связанный тикет: слова могут вообще не пересекаться ("логин парольмен
кіре алмай отыр" и "email/password ауыстыру сұранысы" — тот же случай, но
ни одного общего слова). Когда включён тогл **"✨ ИИ-описания"**, перед тем
как завести новый тикет, бот проверяет — нет ли уже активного (не решённого,
за сегодня) тикета от этого же Telegram-автора в этом же чате
(`findSameAuthorActiveIssue` в вебхуке), и если есть, спрашивает ИИ
(`isSameRequestFollowUp` в `src/lib/ai.ts`), тот же это запрос или нет.
Тот же — сообщение привязывается к существующему тикету
(`usedForIssueId`, без ссылки на карточке — см. `ATTACH_LINK_POLICY` выше),
новый не заводится. При выключенном тогле или недоступности модели —
прежнее поведение (новый тикет).

Промпт явно различает "тот же случай другими словами" от "тот же тип
проблемы, но другой ученик": Telegram-аккаунт часто принадлежит
менеджеру/куратору, который ведёт нескольких учеников, и следующим
сообщением сообщает про ДРУГОГО ("+тағы бір оқушы, другая почта") — это
второй, отдельный случай, ему нужен свой тикет, а не общая карточка.

**Реплаи, из которых тикет не заводится вообще (без участия ИИ).**
`buildDescription` (`src/lib/ticketDescription.ts`) сразу возвращает `null`
(тикета нет, сообщение остаётся во "Входящих") для двух видов реплаев,
у которых разделить "реальная жалоба" от "человек продолжает разговор" по
одному тексту ненадёжно в принципе:

- **Ответ на сообщение одного из НАШИХ агентов** (`isOwnAgentMessage` в
  вебхуке) — даже развёрнутое, по существу написанное объяснение одного
  сотрудника другому звучит для модели неотличимо от настоящей жалобы.
- **Ответ человека на СВОЁ ЖЕ более раннее сообщение**, у которого ещё нет
  тикета — продолжение своей же мысли ("а если так?", "хотя вот что я имел
  в виду"), а не новое обращение. Если у того сообщения тикет уже есть,
  реплай приклеится к нему как обычно (`attachFollowUpToTicket`) — это
  правило только про случай, когда приклеивать ещё не к чему.

## Библиотека решений ("решали так же")

Половина обращений за день — это два-три повторяющихся сценария, и заметки
о решении у них совпадают почти дословно ("Админкамен өшіріп бердік" —
дважды слово в слово за один день). Печатать это заново каждый раз незачем.

`src/lib/solutionLibrary.ts` ищет среди закрытых за последние 30 дней
тикетов те, что похожи на текущий, и предлагает их заметку:

- **В разборе в Telegram** — кнопка **"💡 Решить так же: …"** отдельной
  строкой. Одно нажатие ставит `RESOLVED` с готовой заметкой и, если
  автоответы включены, предлагает сообщить об этом в чат.
- **На сайте** — в окне "Как решили?" (`ResolveDialog`) до трёх вариантов
  с датой; нажатие подставляет текст в поле, дополнить его можно руками.

Считается Жаккаром (`src/lib/similarity.ts`), а не ИИ: мгновенно,
бесплатно и не зависит от квоты, а подсказка всё равно ничего не решает
сама. Порог выше, чем у подсказки при склейке обращений (0.45 против
0.34): там предлагают посмотреть глазами, а тут подставляют готовый текст
в репорт, и ошибиться дороже. Тикеты без заметки в кандидаты не попадают —
подсказывать по ним нечего.

### Заметка из самой переписки

"Похожее решали так" помогает, только если похожее уже было. Но ответ на
"как решили" почти всегда написан и в первый раз — своими же руками, в
рабочем чате: "админкадан өшіріп бердік, қайта кірсін". Дежурному
оставалось набрать то же самое второй раз, теперь для репорта.

Поэтому окно "Как решили?" при открытии подтягивает подсказку из чата
(`GET /api/issues/[id]/suggest-note`):

1. `src/lib/resolutionNote.ts` достаёт реплики **наших** агентов
   (`OWN_AGENT_TELEGRAM_IDS`), относящиеся к этому тикету. Привязка идёт
   **по цепочке ответов**, а не по одному сообщению: дежурный отвечает то на
   сообщение с проблемой, то на последнее сообщение человека, то на свою же
   предыдущую реплику — и всё это один и тот же разговор. Реплика считается
   нашей, если, поднимаясь вверх по `TelegramMessage.replyToMessageId`
   (до 4 звеньев), упираемся в сообщение этого тикета.

   Отдельный случай — ответ на сообщение человека, которое само тикетом не
   стало (прислал почту, которую мы попросили; она отсеивается как "одни
   учётные данные"). Такое сообщение относим к последнему тикету, о котором
   этот же человек писал до него. Без этой оговорки правило разъезжается:
   один куратор за день заводит несколько обращений, и реплика по второму
   подставлялась бы в первый.

   Цепочка, упирающаяся в **чужой** тикет, отбрасывается совсем — за час в
   чате проходит несколько обращений подряд, и решение соседнего в нашей
   заметке это прямая ошибка в отчёте. Если по цепочкам не нашлось ничего,
   берутся реплики агентов в том же чате по времени — это уже догадка, и
   помечается она иначе ("собрано по переписке", а не "из твоего ответа").
2. `summarizeResolutionNote` (`src/lib/ai.ts`) сжимает их в строку для
   репорта — тот же приём, что у описаний, только на другом конце тикета:
   не что случилось, а что сделали. Имя дописывает код, а не модель:
   выдуманное имя коллеги в отчёте боссам — худшее, что может случиться.
3. Если по репликам не видно, что задачу довели до конца ("қарап
   жатырмыз", уточняющие вопросы), модель отвечает `SKIP`, и подсказки
   не будет — поле останется с прежним дефолтом `"<Имя> шешті"`.

Когда подсказки нет, окно **говорит почему**, а не гасит строку молча:
"выключена вместе с «✨ ИИ-описания»", "не настроены Telegram-id агентов",
"к тикету не привязано сообщение из чата", "в чате нет твоих ответов по
этому тикету", "по переписке не видно, чем закончилось". Пустое место на
месте подсказки неотличимо от поломки, а четыре причины из пяти дежурный
чинит сам. Отдельно от них — "не удалось получить подсказку": разовый
таймаут или квота Groq, и это единственный случай, который лечится
повтором, поэтому строка становится кнопкой "— ещё раз".

Работает под тем же тоглом **"✨ ИИ-описания"**: это ровно та же операция
над тем же тикетом, и заводить ради неё отдельный рубильник значило бы
спрашивать человека дважды про одно решение. Подставленный текст всегда
можно заменить кнопкой **"✍️ Написать самому"** (вернёт дефолт) и
вернуть обратно — **"↩️ Вернуть подсказку"**. Набранное руками подсказка
не затирает: если человек начал печатать раньше, чем пришёл ответ модели,
поле остаётся как есть.

В `callback_data` кнопки лежит только id текущего тикета: два cuid'а не
влезли бы в лимит Telegram в 64 байта, поэтому подсказка пересчитывается в
момент нажатия — заодно исключено, что применится устаревший вариант.

## Объявления во все группы (`/broadcast`)

Наблюдалось живьём: одно и то же сообщение — "Қайырлы күн, ПФ да жөңдеу
жұмыстары жүріп жатыр, аяқталғанда кб береміз" — отправляли руками в
четыре рабочих чата подряд. `/broadcast <текст>` в личке с ботом делает то
же одним сообщением.

Уходит **только после подтверждения**: бот сначала показывает текст и
список групп, куда он пойдёт, и ждёт нажатия. Это сообщение видят сразу
все рабочие чаты, а отменить его потом можно лишь удаляя по одному.
Текст черновика хранится в `BroadcastDraft` — в `callback_data`
подтверждения он бы не поместился.

## Что ИИ знает о нашем проекте

Обращения написаны внутренним жаргоном: «ДТ шықпайды», «ПФ баяу»,
«АА-ға ауыстыру керек». Модель этих сокращений не знает и знать не может —
их придумали внутри компании. Без расшифровки ИИ разбирает обращения
вслепую: видит набор букв там, где стоит конкретная проблема.

`src/lib/projectContext.ts` держит словарь, собранный ИИ **из нашей же
истории решённых тикетов**, и подмешивает его в каждый system-промпт
(описания тикетов, поиск дублей, выбор «Жөнделді/Өзгертілді»). На реальных
данных с первого прогона получилось, например:

```
ДТ      — диагностический тест, который проходят ученики
ПФ      — платформа для прохождения тестов
Админка — административный раздел платформы
```

Кнопка **«🧠 Словарь»** во «Входящих» показывает текущий словарь, даёт
пересобрать его и вписать термин руками.

**Про частоту.** Словарь **используется** на каждом обращении к ИИ (дёшево,
из кэша), а **пересобирается** раз в сутки по cron
(`/api/cron/rebuild-glossary`, 19:30 UTC = 00:30 по Алматы, когда корпус за
день уже полный) плюс по кнопке. Пересобирать на каждое входящее сообщение
незачем: это десятки лишних запросов к модели в день ради данных, которые
за день почти не меняются.

Вписанный руками термин (`auto = false`) автосборка **не перезаписывает**:
если агент уточнил значение, значит модель ошиблась, и повторять её ошибку
не нужно.

## ИИ-описания тикетов (опционально)

По умолчанию описание авто-заведённого тикета чистится регулярками
(`src/lib/textClean.ts`) — быстро и бесплатно, но это просто вырезание
известных паттернов (приветствия, ссылки, логины и т.п.), без понимания
смысла сообщения. Есть опциональная замена: переписывание сообщения через
**Groq** (`src/lib/ai.ts`, бесплатный inference открытых LLM вроде Llama),
который понимает контекст и сам формулирует описание проблемы в стиле
дежурного агента — одна строка-заголовок (обычно 6–14 слов), а не вежливый
пересказ на два предложения и не голый ярлык из общей темы: важно сохранить
всю конкретику по самой проблеме (предмет, класс, четверть, код ошибки, что
именно за действие), но контактные данные и доступы (почта, телефон,
логин/пароль) в описание не попадают — они уходят к агенту отдельными
зацепками. А не просто вычищает мусор. Groq выбран вместо Gemini из-за
free tier без привязки карты — у Gemini free-tier квота на самом деле
равна 0, пока не подключишь биллинг (а подключение биллинга у Google
регулярно ломается собственным багом `OR_BACR2_44`).

**Как включить:**

1. Получи бесплатный API-ключ на [console.groq.com/keys](https://console.groq.com/keys)
   — вход через Google-аккаунт, без привязки карты.
2. Добавь `GROQ_API_KEY` в `.env` локально и/или в Environment Variables
   на Vercel (см. "Деплой на Vercel" выше). Без ключа тогл в интерфейсе
   ничего не сломает — просто молча продолжит работать на регулярках.
3. В `/inbox` включи тогл **"✨ ИИ-описания"** в шапке (виден и на вкладке
   "Сообщения", и на "Доске"). Настройка общая на всё приложение, а не
   личная (хранится в таблице `AppSetting`, единственная строка), и
   применяется к каждому новому входящему сообщению из уже привязанного
   чата (`POST /api/telegram/webhook`) до появления тикета на доске.
4. При необходимости замени модель через `GROQ_MODEL` (по умолчанию
   `llama-3.3-70b-versatile`).

**Важно про надёжность:** вебхук должен ответить Telegram быстро, поэтому
при любой ошибке — нет ключа, Groq не ответил вовремя (таймаут 8 сек),
вернул пустой ответ — код молча откатывается на обычную regex-чистку, а не
роняет обработку сообщения. Тикет в любом случае будет заведён.

**Несколько ключей (запасной аккаунт):** бесплатная квота Groq — 100k
токенов/день, лимит висит на аккаунте целиком, а не на конкретном ключе,
так что второй ключ того же аккаунта её не обходит. `GROQ_API_KEY`
принимает список через запятую (`"key1,key2"`) — при 429/ошибке/таймауте
одного ключа `callGroqChat` (`src/lib/ai.ts`) автоматически пробует
следующий по порядку. Чтобы это реально помогало, второй ключ должен быть
с другого Groq-аккаунта (заведённого на другую почту).

ИИ так же решает, что сообщение вообще не стоит тикета: на приветствие,
голую ссылку или "рахмет" модель по промпту отвечает ровно `SKIP`, и тикет
не заводится (см. `AI_SKIP` в `src/lib/ai.ts`). До обращения к ИИ то же
самое проверяется дешёвыми регулярками (`isNoiseOnly`), так что на
очевидный мусор запрос к API вообще не уходит.

То же `SKIP` — и на рабочую переписку коллег внутри группы поддержки
(методисты, тимлиды и т.п. обсуждают между собой процессы/инструкции/
версии тестов), которая не является обращением ученика/родителя, но по
форме похожа на сообщение о проблеме. Реальный пропущенный случай — в
промпте отдельным few-shot примером: рабочий чат обсуждал версии ҰБТ-теста
("иә олар бастап қойған сол нұсқамен тапсырып жатыр" — обычное
подтверждение внутри обсуждения), а модель цеплялась за слово "нұсқа" и
заводила тикет вроде "Нұсқа бойынша тапсырып жатыр".

**Если ИИ написал не то:** в форме редактирования тикета (когда тогл
включён и у тикета есть исходное Telegram-сообщение) над полем описания
есть кнопка **"ИИ написал не то?"** — показывает исходный текст сообщения и
кнопку "Вставить вариант без ИИ", которая подставляет в поле ту же
regex-чистку, что работает при выключенном ИИ (`GET
/api/issues/[id]/raw-source`). Дальше можно и оставить как есть, и
дописать своими словами — просто более предсказуемая отправная точка, чем
вычищать чужой ИИ-текст руками. Исходное сообщение ищется по совпадению
`telegramLink` тикета с `messageLink` в `TelegramMessage` — отдельного
поля с сырым текстом на `Issue` нет.

Ручное редактирование/создание тикета в форме (`IssueForm`) тогл не
использует при сохранении — там всегда обычная regex-чистка
(`PATCH`/`POST /api/issues`), без обращения к внешнему API: это
интерактивное сохранение, где агент сам видит и правит текст, лишняя
задержка ни к чему.

**"✨ ИИ напишет"** — отдельная явная кнопка над полем описания (видна,
когда там есть текст), не зависит от тогла и не привязана к вебхуку.
Для случая, когда агент вставляет в поле описания сырой скопированный
текст сообщения (например, из чата, куда бот не подключён — см. "Тикет
по ссылке, которой нет во 'Входящих'" выше) и хочет получить короткое
описание в стиле тикета, а не сокращать вручную. Дёргает
`POST /api/ai/rewrite-description` → тот же `rewriteTicketDescriptionWithAI`,
что и в вебхуке; если модель отвечает `SKIP` (не похоже на обращение) или
недоступна — текст в поле не трогается, показывается сообщение вместо
него.

## ИИ-поиск дублей за день

Кнопка **"🤖 Найти дубли"** на доске "Входящих" (видна, если тикетов за
день ≥ 2) спрашивает Groq, нет ли среди тикетов дня нескольких карточек
про один и тот же запрос ("доступ беру" от одного и того же ученика,
пришедший тремя отдельными сообщениями). Модель получает список
`id: описание` и возвращает JSON-группы совпадений
(`findDuplicateGroups` в `src/lib/ai.ts`, `POST /api/issues/duplicates`).

Это **только подсказка** — как и Жаккар-похожесть в `src/lib/similarity.ts`
при ручном приклеивании, автоматически ничего не объединяется. Найденные
группы показываются панелью над доской, для каждой — "Объединить"
(схлопывает через уже существующий `merge-into`) или "Скрыть". Если ключ
не задан или Groq недоступен — панель не появляется, в тосте
`ИИ недоступен`, а не молчаливое "дублей нет" (это разные состояния: см.
поле `unavailable` в ответе роута).

## Перепроверка авто-тикетов ИИ-ом

Кнопка **"🤖 Проверить авто-тикеты"** на доске "Входящих" (видна, если за
день есть тикеты в "Отправлено", заведённые ботом без агента —
`createdBy === "Бот"`) — на случай, если такие тикеты завелись, пока ИИ
был выключен, упал по таймауту или упёрся в дневную квоту Groq (см.
"ИИ-описания тикетов" выше), и остались на обычной regex-чистке.
Перепрогоняет каждый такой тикет через тот же `rewriteTicketDescriptionWithAI`
(`POST /api/issues/ai-validate`), что применяется к новым сообщениям, и
показывает две группы находок:

- **Похоже на рабочую переписку, не обращение** — ИИ ответил `SKIP` (см.
  "рабочая переписка коллег" в примерах промпта), то есть при живом ИИ
  тикет вообще не завёлся бы. Кнопки "Удалить" / "Оставить".
- **Описание можно точнее** — ИИ предложил другую формулировку. Кнопки
  "Применить" / "Оставить как есть".

Как и поиск дублей — **только подсказка**, ничего не удаляется и не
переписывается само, решение по каждому тикету за агентом.

## Поиск пропущенных тикетов во "Входящих"

Кнопка **"🔍 Найти пропущенные тикеты"** на вкладке "Сообщения" (видна,
если за день есть хоть одно сообщение) ловит другой разрыв: сообщения, у
которых уже известна группа, но тикет по ним так и не завёлся. Самая
частая причина — не сбой ИИ (при нём и так тихая regex-чистка, тикет всё
равно создаётся, см. выше), а привязка чата **задним числом**: когда
впервые выбираешь группу для чата вручную (`PATCH
/api/telegram/messages/[id]`), у всех уже накопленных сообщений этого чата
проставляется правильная группа — но тикеты за них не заводятся, это
осознанно оставлено на "Создать тикет" вручную по каждому.

`POST /api/telegram/ai-recheck-messages` прогоняет каждое такое сообщение
через ту же логику, что и вебхук в момент получения (`buildDescription` в
`src/lib/ticketDescription.ts` — общий код для обоих мест), и предлагает
завести тикет по тем, что теперь проходят: панель со связкой
"текст → предложенное описание" и кнопками "Создать тикет" / "Скрыть".
Работает независимо от ИИ (регулярки — не менее надёжный путь, чем в
вебхуке), так что не зависит от квоты Groq.

## Ревью и отправка репорта через Telegram

Идея: сайт неудобен с телефона, а ревью дня и отправку репорта боссам
дежурному часто нужно делать именно с телефона — поэтому всё это можно
сделать прямо в Telegram, не заходя на сайт. Общая логика — в
`sendDailyReviewMessage` (`src/lib/dailyReview.ts`), её дёргают два
cron'а с разным назначением:

- **`GET /api/cron/evening-report`** — Vercel Cron, `"0 17 * * *"` UTC =
  22:00 по Алматы. Обзор **сегодняшнего** дня.
- **`GET /api/cron/morning-report-check`** — `"0 4 * * *"` UTC = 09:00 по
  Алматы. Не все дежурные закрывают день ровно в 22:00 — часть разбирает
  вчера с утра. Проверяет **вчерашнюю** дату: если репорт уже отправили
  вечером (см. `ReportSendLog` ниже) — молча ничего не делает; если нет —
  присылает то же самое повторно, чтобы вчерашний день не потерялся.

Оба присылают личным сообщением:

- **Сам текст репорта** (тот же `generateReportText`, что и на сайте) —
  не просто цифры, а буквально то, что уйдёт в группу, чтобы ревью было
  настоящим, а не вслепую. Длиннее лимита Telegram (4096 символов) —
  обрезается с припиской "полный текст — на сайте".
- Кнопку **"📤 Отправить в группу"** — шлёт этот же текст в
  `REPORT_TARGET_CHAT_ID` (`report_send:<дата>` в `handleCallbackQuery`,
  `src/app/api/telegram/webhook/route.ts`) и одновременно пишет в
  `ReportSendLog` (модель в `prisma/schema.prisma`, единственное поле —
  `reportDate`, по нему и определяется "уже отправляли или нет" для
  утренней проверки). Пока `REPORT_TARGET_CHAT_ID` не задана — Telegram
  покажет алерт "группа ещё не настроена", ничего не сломается.
- Кнопку **"🔍 Начать разбор тикетов (N)"** (видна, только если есть что
  разбирать) — не запускается сама, отдельная явная кнопка: сначала видно
  репорт целиком, разбор дежурный начинает, когда готов. По нажатию снимает
  только себя из клавиатуры (`"Отправить в группу"` рядом остаётся рабочей)
  и запускает разбор нерешённых тикетов **по одному** — карточка одного
  тикета (группа, описание, компактная кликабельная 🔗-ссылка вместо голого
  URL) с кнопками действий; после любого действия карточка сама переезжает
  к следующему тикету, редактируя то же сообщение (`editMessageText`), а не
  рассылая новые. Раньше пробовали и отдельный баббл на каждый тикет (стена
  из N сообщений), и сетку кнопок под одним пронумерованным списком (стена
  кнопок — 4 на тикет, на 10+ тикетов уже нечитаемо) — обе версии
  оказались хуже, чем один тикет за раз.
  - В очередь попадают только **SENT/PENDING/IN_PROGRESS**
    (`REVIEWABLE_STATUSES` в `dailyReview.ts`) — ESCALATED туда не входит:
    тикет уже передан другой команде, пересматривать его каждый день не
    задача дежурного (RESOLVED и так не в очереди).
  - Очередь (какие тикеты и в каком порядке) фиксируется в момент старта
    разбора и хранится в `ReviewSession` (`prisma/schema.prisma` —
    `chatId` как первичный ключ, то есть одна активная сессия на чат;
    `ticketIds` — очередь, `currentIndex` — позиция в ней,
    `messageId` — что редактировать). Реализация — `buildTicketCard` /
    `startReviewSession` / `advanceReviewSession` в
    `src/lib/dailyReview.ts`.
  - На карточке до 5 кнопок (пропускаются, если уже неактуальны для
    текущего статуса): **"🔄 В работе"**, **"⏳ Пендинг"**, **"⚠️ Передать"**,
    **"📝 Заметка"**, **"✅ Решено"**, плюс отдельной строкой
    **"⏭ Пропустить"** (не трогает статус, просто идёт к следующему) и,
    начиная со второго тикета в очереди, **"⬅️ Назад"** — возвращает к
    предыдущему тикету очереди (`goBackReviewSession` в `dailyReview.ts`,
    `back_ticket:<issueId>` в вебхуке), если промахнулись мимо кнопки или
    пропустили не то. Как и при движении вперёд, тикеты, выпавшие из
    `REVIEWABLE_STATUSES` по дороге, пропускаются и при возврате назад.
    - **"📝 Заметка"**, **"✅ Решено"**, **"⏳ Пендинг"** — общий механизм:
      кнопкой текст не набрать, поэтому бот шлёт отдельное сообщение с
      просьбой ответить (Reply) на него текстом (`sendNotePrompt` в
      вебхуке); связь "на какой тикет, с каким статусом" хранится в
      `PendingNotePrompt` (одноразовая, удаляется сразу после того, как
      ответ пришёл) — см. перехват реплая в `POST`-хендлере вебхука, до
      проверки `isOwnAgentMessage` (иначе собственный ответ агента
      архивировался бы молча, не долетев до этой ветки). "Решено"/"Пендинг"
      дополнительно несут `targetStatus` в `PendingNotePrompt` — статус
      применяется вместе с текстом заметки по приходу ответа (по аналогии
      с `ResolveDialog` на сайте: без текста "как решили" статус применять
      нет смысла — именно эта заметка попадёт в репорт для боссов). У
      обычной "📝 Заметка" `targetStatus` не задан — меняется только текст.
      После сохранения — основная карточка переходит к следующему тикету.
    - **"⚠️ Передать"** — статус ESCALATED без выбранной команды не имеет
      смысла, поэтому кнопка не меняет статус сама, а шлёт отдельное
      сообщение с кнопками команд (`ESCALATION_TEAMS`,
      `ISSUE_ESCALATE_PREFIX` → `ISSUE_ESCALATE_TEAM_PREFIX` в вебхуке);
      после выбора команды основная карточка тоже переходит дальше.
  - Если по дороге тикет оказался решён где-то ещё (например, на сайте) —
    `advanceReviewSession` пропускает его тоже, а не показывает
    неактуальную карточку. Когда очередь заканчивается — сообщение
    переписывается в "✅ Все тикеты дня разобраны!" без кнопок, `ReviewSession`
    удаляется.
- Кнопку **"🔗 Найти похожие тикеты"** (видна, только если задан
  `GROQ_API_KEY` и тикетов за день хотя бы два) — та же ИИ-подсказка
  "вероятно, это одно и то же обращение", что и кнопка **"🤖 Найти дубли"**
  во "Входящих" (`findDuplicateGroups` в `src/lib/ai.ts`), но вместо панели
  на сайте группы разбираются по одной через Telegram — той же
  один-за-одним механикой, что и обычный разбор тикетов
  (`src/lib/dedupeReview.ts`, `start_dedupe:<дата>` в вебхуке). По нажатию
  снимает только себя из клавиатуры, остальные кнопки сводки остаются
  рабочими.
  - Карточка группы показывает все описания в ней и две кнопки:
    **"✅ Объединить"** (`dedupe_merge`) и **"⏭ Пропустить"**
    (`dedupe_skip`) — коллбэки без параметров, текущая группа читается из
    `DuplicateReviewSession` по `chatId`, а не из `callback_data` (в
    отличие от разбора тикетов, тут нечего туда класть — вся очередь и так
    завязана на чат).
  - **"✅ Объединить"** схлопывает всю группу в один тикет — самый ранний
    по `position` остаётся, остальные вливаются в него по очереди через
    общий `mergeIssueInto` (`src/lib/mergeIssue.ts`, теперь используется и
    сайтом, и ботом — раньше транзакция объединения жила только в
    `POST /api/issues/[id]/merge-into`). Автор схлопнутого в цель тикета
    переоформляется на того, кто нажал (`telegramIdToAgent`, либо
    `SHARED_AGENT` — "Дежурный" — если id не сопоставлен), но только если
    целевой тикет ещё числился за ботом — та же логика, что у
    ручного объединения на сайте.
  - **"⏭ Пропустить"** ничего не трогает, просто идёт к следующей группе.
  - Как и у разбора тикетов, очередь групп фиксируется в момент старта
    (`groupsJson` — сериализованный `string[][]`, Prisma `String[]` не
    умеет массив массивов) и хранится в `DuplicateReviewSession`
    (`prisma/schema.prisma`) — одна активная сессия дублей на чат, не
    мешает параллельно активной `ReviewSession` обычного разбора (разные
    модели). Когда очередь групп заканчивается — сообщение переписывается в
    "✅ Разбор похожих тикетов завершён!", `DuplicateReviewSession`
    удаляется.

**Команды в личке с ботом.** Всё выше (сводка, разбор, дубли, отправка)
привязано к вечернему/утреннему cron — если понадобилось посреди дня, ждать
не нужно: те же действия доступны слэш-командами прямо в личном чате с
ботом (`handleBotCommand` в `src/app/api/telegram/webhook/route.ts`).
Работают только для известных агентов (`telegramIdToAgent` по
`AGENT_TELEGRAM_IDS`, см. ниже — незнакомый id получит вежливый отказ) и
только в приватном чате: в группах поддержки бот команды не слушает, чтобы
внутренние данные не улетели в чат с клиентами. Необязательный второй
аргумент — дата `YYYY-MM-DD`, без него — сегодня.

- **`/report [дата]`** — та же сводка, что шлёт вечерний cron
  (`buildReviewSummary`, общая функция с `sendDailyReviewMessage`), только
  сразу в ответ спросившему, а не тому, кто больше всех писал в тот день.
- **`/send [дата]`** — отправляет репорт в `REPORT_TARGET_CHAT_ID` напрямую,
  без захода в `/report`. Общая с кнопкой "📤 Отправить в группу" логика
  (`sendReportToGroup` в `src/lib/reportSend.ts`) теперь **сама** не даёт
  отправить дважды за одну дату — проверяет `ReportSendLog` до отправки, а
  не только пишет в него после: если уже отправляли, просто сообщает время
  предыдущей отправки вместо повторной рассылки в чат с боссами. Раньше это
  было на совести того, кто жал кнопку не глядя.
- **`/dedupe [дата]`** — запускает разбор похожих тикетов (см. выше), не
  дожидаясь вечерней сводки.
- **`/review [дата]`** — запускает разбор тикетов по одному, не дожидаясь
  вечерней сводки.
- **`/autoreply [on|off]`** — включает и выключает автоответы бота в рабочих
  группах (см. «Автоответы бота» выше). Без аргумента показывает текущее
  состояние и короткую памятку о том, что именно бот делает сам, а что
  только по кнопке.
- **`/broadcast <текст>`** — объявление во все привязанные группы разом
  (см. «Объявления во все группы» ниже). Спрашивает подтверждение.
- **`/readchat [on|off]`** — бот читает твои ответы в группах и сам ставит
  статусы (см. «Обратная связь: из чата в статус»). Рубильник отдельный от
  `/autoreply` намеренно: там бот пишет коллегам, тут молча меняет то, что
  уйдёт в репорт боссам.
- **`/help`** (или `/start`) — список команд текстом.

Автодополнение команд при наборе "/" в Telegram — отдельный шаг,
регистрируется один раз через `setMyCommands` (см. "Настройка
Telegram-бота" выше); сами команды работают и без него.

**Кому шлём.** В системе нигде явно не записано, кто дежурил в конкретный
день, поэтому получателя вычисляем по факту: тот из агентов, кто в тот
день больше всех писал в привязанные чаты (`TelegramMessage.fromId`,
`pickRecipient` в `lib/dailyReview.ts`). Для утренней проверки — это
"кто дежурил вчера", а не "кто дежурит сегодня": напоминание про вчерашний
день логичнее адресовать вчерашнему дежурному, он лучше знает контекст.
Это стало возможным только после того, как свои сообщения агентов начали
сохраняться (archived), а не отбрасываться целиком (см. "Свои сообщения
не попадают во 'Входящие'" выше) — раньше посчитать было не по чему.

Инлайн-кнопки смены статуса (и под тикетами в сводке, и в принципе везде,
где вебхуку придёт `callback_query` с `issue_status:<id>:<статус>`)
обрабатываются там же. Реакция бота на исходное сообщение и переоформление
автора с "Бот" на живого агента при этом работают так же, как при смене
статуса на сайте — общая логика вынесена в `src/lib/issueStatus.ts`, чтобы
два места (сайт и Telegram) не разъезжались. Автора здесь определяем по
`callback_query.from.id` через `AGENT_TELEGRAM_IDS` (см. ниже), а не по
сессии — в Telegram её нет.

**Новые переменные окружения** (в `.env` и/или Vercel Environment
Variables):

- `CRON_SECRET` — Vercel сам добавляет заголовок `Authorization: Bearer
  <значение>` к запросам от обоих cron'ов; без совпадающего значения
  эндпоинты всегда отвечают 401 (в том числе если переменная вообще не
  задана — открытыми эти триггеры быть не должны).
- `AGENT_TELEGRAM_IDS` — те же Telegram id, что в `OWN_AGENT_TELEGRAM_IDS`,
  но с именами: `"Ерош:123456789,Алпа:987654321"`. Отдельная от
  `OWN_AGENT_TELEGRAM_IDS` переменная, чтобы не менять формат уже рабочего
  прод-фильтра ради новой фичи.
- `REPORT_TARGET_CHAT_ID` — необязательная, чат для кнопки "Отправить в
  группу"; можно добавить позже, без неё всё остальное продолжает работать.
  Для супергрупп это отрицательное число вида `-100...` — узнать можно,
  временно добавив в чат стороннего бота вроде `@RawDataBot`, он сразу
  пришлёт JSON с `chat.id` (не `getUpdates` у своего бота — конфликтует с
  уже активным вебхуком, см. `getWebhookInfo`/`deleteWebhook` в доке
  Telegram Bot API).
- `REPORT_TARGET_THREAD_ID` — необязательная, только если в чате из
  `REPORT_TARGET_CHAT_ID` включены "Темы" (форум-топики) и репорт должен
  уходить именно в конкретную тему, а не в общий поток. Число из ссылки на
  тему (`https://t.me/c/<chat>/<номер>` — `<номер>` это и есть
  `message_thread_id`). Передаётся в `sendTelegramMessage` четвёртым
  аргументом (`src/lib/telegram.ts`).

## Смена почты ученику (опционально)

Страница `/platform/change-email` (пункт меню **"Почта"**) меняет почту
ученику в **основной платформе JUZ40** — это отдельная система со своим API
(`api.juz40-edu.kz`), не наша БД. Support сюда только ходит клиентом.

Как это работает:

- **Аутентификация — сервис-аккаунтом** (`PLATFORM_SERVICE_USERNAME` /
  `PLATFORM_SERVICE_PASSWORD`), а не токеном конкретного агента: логинимся
  раз, кэшируем JWT до истечения, релогинимся при `401`
  (`src/lib/platform.ts`). Креды живут только на сервере.
- **Read-modify-write.** Эндпоинт платформы `POST /v1/admin/users/{id}/change`
  принимает **весь** объект пользователя, а не одно поле. Поэтому сначала
  читаем текущий объект (`GET /v2/users/{id}`), потом переотправляем его
  целиком, поменяв только почту. Маппинг вложенного ответа чтения в плоское
  тело записи сверен с тем, что шлёт сама админ-панель платформы (в т.ч.
  `parentFirstname`/`parentLastname` = `null`) — инструмент делает ровно то
  же, что человек в её UI, так что затереть соседние поля не может.
- **email и username — это логин ученика, меняются вместе** (у платформы нет
  отдельного поля `email`, `username` и есть почта).
- **Журнал.** Каждая смена пишется в `PlatformEmailChange` (кто из агентов,
  какому ученику, `oldEmail → newEmail`, когда) — мы меняем прод-данные
  учеников, поэтому "кто это сделал" фиксируется. `actor` берётся из сессии
  (`getCurrentIdentity().name`), не из клиента.
- **Выключено по умолчанию.** Пока не заданы все три `PLATFORM_*` —
  `platformEnabled()` = false, страница отдаёт заглушку, а пункт меню
  "Почта" не появляется (флаг едет в `/api/auth/me` → `AppHeader`). Так фича
  катится выключенной и включается человеком, задав env на Vercel.
- **VPN не нужен:** API платформы публичный (в отличие от её БД и
  Elastic-логов, которые за VPN), поэтому серверные роуты Support на Vercel
  достают до него без туннелей.

### Кнопка прямо на карточке тикета

Когда в обращении распознан запрос «смените почту A → B», на карточке
(канбан во «Входящих») появляется кнопка **«✉️ Сменить почту →»**, которая
открывает инструмент с уже подставленными почтами — агенту остаётся выбрать
ученика и подтвердить. Бот только предлагает; смену по-прежнему делает
человек.

Распознавание (`src/lib/emailChangeRequest.ts`) — по **сырому** тексту
обращения (в `description` почты уже вычищены), считается в
`GET /api/issues` и только когда инструмент включён. Срабатывает на
**намерение замены + ровно две почты**: «ескі/жаңа почта», «қате … дұрыс»,
«қатесі/дұрысы», «ауыстыру», русские «старая/новая почта»,
«поменять/заменить/сменить». Именно намерение (а не просто «две почты в
тексте») отсекает списки учеников на приглашения/оплаты/результаты — там
почт тоже две и больше, но это не запрос смены. Направление «где старая, где
новая» берётся из слова-маркера рядом с адресом, а инструмент дополнительно
проверяет по платформе, какая почта реально текущая.

## Логи ученика (опционально)

Страница `/logs` (пункт меню **"Логи"**) — прямой поиск по логам
Elasticsearch, тем же самым, что раньше искали руками в Kibana. Логи лежат за
корпоративным VPN, а Support на Vercel serverless и не может держать
постоянный туннель — поэтому туннель и сам поиск вынесены в отдельный, всегда
включённый сервис [`juz40-vpn-logs`](../juz40-vpn-logs), а Support ходит к
нему обычным HTTPS с bearer-токеном (`src/lib/logsClient.ts`).

```
Support (Vercel) --HTTPS + токен--> juz40-vpn-logs (всегда-включённый хост)
                                        --WireGuard--> Elasticsearch
```

Как это работает:

- **Два режима поиска** — по email ученика (точная фраза по всем полям) и
  свободный запрос в синтаксисе Elasticsearch `query_string`
  (`src/components/LogsExplorer.tsx`). Пресеты периода — 1ч/24ч/7д/30д (логи
  живут ~15-30 дней, дальше смотреть нечего); смена периода над уже
  показанными результатами сразу перезапускает поиск.
- **Токен сервиса не покидает сервер.** Браузер ходит только на свои же
  `/api/logs/search` и `/api/logs/student`, которые прокидывают запрос
  дальше с `LOGS_SERVICE_TOKEN` из env — как и `PLATFORM_*` у смены почты.
- **Кнопка «🪵 Логи» на карточке тикета** — рядом с уже распознанной почтой
  ученика (`ticketHints.ts`), открывает `/logs?email=...` с уже вписанным
  адресом и сразу выполняет поиск. Мирроит кнопку «Сменить почту →».
- **Сервис можно выключить прямо со страницы** — WireGuard пускает только
  один активный пир на конфиг, поэтому пока сервис держит корпоративный
  туннель, тот же `.conf` нельзя одновременно поднять на личной машине.
  Кнопка в шапке страницы (`VpnServiceButton`, `src/lib/vpnService.ts`)
  включает/выключает три контейнера на VM по SSH. Если поиск упёрся в
  выключенный сервис или недоступный туннель — прямо в баннере ошибки есть
  кнопка «Включить и повторить».
- **Выключено по умолчанию.** Пока не заданы `LOGS_SERVICE_URL` и
  `LOGS_SERVICE_TOKEN` — `logsServiceEnabled()` = false, страница отдаёт
  заглушку, а пункт меню "Логи" не появляется (флаг едет в `/api/auth/me` →
  `AppShell`, тот же паттерн, что у "Почты"). Управление сервисом
  (`VPN_VM_HOST`, `VPN_VM_USER`, `VPN_VM_SSH_KEY_B64` — адрес VM и
  base64-код приватного SSH-ключа) — отдельный набор env, независимый от
  доступа к самим логам.
### ИИ-разбор логов (кнопка «🤖 Разобраться с ИИ»)

Поиск отвечает на вопрос «что было в логах», разбор — на вопрос «что из
этого следует». Агент описывает ситуацию словами ученика («сдал тест, а
результата нет»), модель читает найденные записи и возвращает **хронологию с
привязкой к конкретным записям**: время → что произошло → `requestId`, плюс
вывод в одну-две фразы. Это то, чем агент говорит с учеником фактами, а не
«у нас всё работает».

Как это устроено (`investigateStudentLogs` в `src/lib/ai.ts`,
`POST /api/logs/investigate`):

- **Модели уходит не всё подряд.** Из каждой записи берутся только время,
  метод, URI, статус, `requestId`, `message`; служебные поля
  filebeat/kubernetes (а это больше половины документа) отбрасываются. Тела
  запроса/ответа обрезаются до 200 символов и шлются только там, где отвечают
  на вопрос «что пошло не так» — у ошибок и у запросов, которые что-то меняют
  (не GET). Это не педантизм: дневная квота Groq общая на весь аккаунт, и
  один жирный разбор способен высадить её у авто-описаний тикетов из вебхука.
- **Время приводится к Алматы до отправки модели.** В документе оно в UTC, а
  в таблице агент видит Алматы (+5). Если бы модель честно повторила UTC,
  разбор говорил бы «09:35» ровно над строкой таблицы «14:35» — и агент
  назвал бы ученику время, которого не было.
- **Обрезка окна видна.** Модели уходит не больше 60 самых свежих записей
  (сортируем сами, не полагаясь на порядок от сервиса логов). Если найдено
  больше — панель прямо пишет, сколько записей осталось за кадром: иначе
  «в логах этого нет» читалось бы как факт, хотя нужная запись могла просто
  не попасть в окно.
- **Выдуманные ссылки на записи помечаются.** Модель может сослаться на
  `requestId`, которого ей не давали. Ссылка убирается, но событие получает
  метку «не подтверждено записью»: без неё выдумка выглядела бы неотличимо
  от честного события без id. Число таких событий уходит в лог — это
  регрессия модели, и увидеть её надо раньше, чем по жалобам агентов.
- **Пустая хронология — не молчание, а предупреждение.** Вывод без единой
  ссылки на запись показывается с явной плашкой «ничем не подтверждён,
  пересказывать ученику нельзя»: уверенная фраза и уверенная фраза с девятью
  ссылками не должны выглядеть одинаково.
- **«Модель не ответила» ≠ «в логах ничего нет».** Первое — повод повторить,
  второе — валидный ответ с пустой хронологией и объяснением в `summary`.
  Панель говорит об этих случаях разными словами.
- **Выключено по умолчанию, отдельным рубильником** (`logsAiEnabled`, не
  общий с «✨ ИИ-описания»): риск другой — в описаниях во внешнюю модель
  уходит текст обращения, а здесь тела запросов и ответов платформы, где
  попадаются ссылки восстановления пароля и токены. Включается прямо в
  панели разбора, с явным предупреждением об этом.
- Открыт с карточки тикета — поле «опиши ситуацию» **предзаполнено описанием
  тикета**, агенту остаётся один клик.

## Возможные доработки на будущее

- Автоматический перенос нерешённых ("Пендинг") тикетов на следующий день.
- Drag & drop для сортировки групп/тикетов вместо стрелок.
- Real-time обновление "Входящих" через WebSocket/SSE вместо опроса каждые 15 секунд.
- SLA-подсветка: тикет в "Отправлено" дольше N часов — заметная рамка на доске.
- Дайджест "висяков" по утрам — тикеты, которые вторые-третьи сутки не в "Решено".
