# Support Reports — обзор проекта

Внутренний инструмент для JUZ40 (онлайн-образование), заменяющий ручное
ведение support-репорта в Telegram. Два постоянных агента — **Ерош** (это
пользователь, с которым обычно идёт работа в этом чате) и **Алпа** — плюс
общий аккаунт **Дежурный** для сменных/выходных саппортов.

## Стек

- Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4
- Prisma 7 (driver adapters, `@prisma/adapter-pg`) + Postgres (Vercel/Neon)
- Своя сессионная аутентификация (HMAC-подписанная кука), без NextAuth и т.п.
- Деплой на Vercel; сборка сама гоняет `prisma generate && prisma migrate deploy && prisma db seed` (см. `package.json` → `build`)

Подробности по установке/деплою/настройке Telegram-бота — см. `README.md`,
он поддерживается в актуальном состоянии и там же описано текущее поведение
каждой фичи.

## Модель данных (`prisma/schema.prisma`)

- **`Issue`** — тикет: `reportDate` (`YYYY-MM-DD`), `groupName`/`groupEmoji`,
  `position` (ручной порядок), `description`, `telegramLink`, `status`
  (`IssueStatus`), `note`, `ticketLink` (Jira/Atlassian), `createdBy`,
  таймстемпы.
- **`IssueStatus`** enum: `SENT` (дефолт для новых тикетов) → `IN_PROGRESS` /
  `PENDING` (по сути один рабочий процесс, UI их объединяет) → `RESOLVED`.
  Метаданные статуса (лейбл, эмодзи, tailwind-классы, дефолтная заметка) —
  централизованы в `src/lib/status.ts` (`STATUS_META`).
- **`GroupPreset`** — 4 дефолтные группы поддержки с фиксированным
  порядком + `chatId` (привязка Telegram-чата к группе, заполняется один раз
  вручную через UI, дальше все сообщения из этого чата автоматически идут в
  нужную группу).
- **`TelegramMessage`** — сырые входящие сообщения из бота: `chatId` +
  `messageId` (уникальная пара), `fromId` (BigInt — id пользователей Telegram
  часто не помещаются в Int32), `text`, `usedForIssueId` (связь с
  авто-заведённым тикетом), `archived`/`viewed` флаги.

## Как это всё связано (mental model)

1. Telegram-бот шлёт апдейты на вебхук `POST /api/telegram/webhook`
   (`src/app/api/telegram/webhook/route.ts`).
2. Свои же сообщения агентов (ответы прямо в группе) отфильтровываются по
   числовому `from.id` через `OWN_AGENT_TELEGRAM_IDS` — не должны попадать в
   тикеты.
3. Если сообщения от одного и того же человека приходят с разрывом < 5 минут
   — они склеиваются в один `TelegramMessage` (и, если уже есть привязанный
   тикет, описание тикета тоже обновляется).
4. Если `chatId` уже привязан к группе (`GroupPreset.chatId`) — тикет
   заводится **автоматически**, статус `SENT`, автор `"Бот"`
   (`AUTO_ISSUE_CREATOR` в `src/lib/telegram.ts`). Если группа ещё не
   известна — сообщение просто ложится во "Входящие", группу выбирают
   вручную один раз.
5. Текст автотикета прогоняется через `cleanTicketDescription`
   (`src/lib/textClean.ts`) — чисто регулярками, без внешних API: убирает
   казахские/русские приветствия, голые ссылки, email, телефоны,
   логин/пароль строки, плейсхолдеры вложений (`[Фото]`/`[Видео]`/…) и их
   ярлыки. Если чистка оставила бы тикет пустым — возвращается исходный
   текст (лучше грязный тикет, чем пустой).
6. Как только живой агент что-то делает с авто-тикетом (меняет статус,
   редактирует) — `createdBy` молча переходит с `"Бот"` на его имя
   (server-side, по сессии — см. `PATCH /api/issues/[id]`), клиент это поле
   не присылает и не может подделать.
7. **`/inbox`** ("Входящие") — рабочее место разбора дня, вкладки
   Сообщения / **Доска** (Доска — дефолтная). Доска — канбан в 3 колонки
   (Отправлено / В работе+Пендинг / Решено), drag-and-drop между ними,
   опрос сервера каждые 15 сек (`POLL_INTERVAL_MS` в `Inbox.tsx`).
8. **`/`** (Дашборд, "Сегодня") и **`/history`** — репорт по дате: список
   тикетов по группам + живой предпросмотр текста репорта +
   "Скопировать". `generateReportText` (`src/lib/report.ts`) **исключает
   тикеты со статусом `SENT`** из текста репорта (ещё ничего не произошло —
   рано выносить), но они всё равно видны в списке на странице.

## Важные неочевидные вещи (грабли, на которые уже наступали)

- **JS `\b` не видит кириллицу.** `\b` зависит от `\w`, а `\w` по умолчанию
  ASCII-only — `\bлогин\b` тихо не матчится вообще. Для юникод-границ слова
  используй lookaround: `` (?<![\p{L}\p{N}])слово(?![\p{L}\p{N}]) `` с
  флагом `u`. См. `CREDENTIAL_PAIR` в `src/lib/textClean.ts`.
- **Автор тикета никогда не приходит от клиента** — он либо `AUTO_ISSUE_CREATOR`
  при авто-создании, либо `getCurrentIdentity()` на сервере при ручном
  создании/редактировании/auto-claim. Не добавляй `createdBy` в тело запроса
  с фронта.
- **Массовые/ретроактивные изменения данных — только через явный
  user-triggered эндпоинт + кнопку**, никогда не через миграцию, которая
  сама накатится при следующем деплое на Vercel (пример — `POST
  /api/issues/normalize-status`, `POST /api/issues/clean-descriptions`).
  Прод-миграции с `UPDATE ... WHERE ...` для данных — плохая идея, это уже
  блокировалось как небезопасное автоприменение.
- **Kanban — нативный HTML5 drag-and-drop**, без внешней библиотеки
  (`draggable` + `onDragStart`/`onDragOver`/`onDrop` в `KanbanBoard.tsx`).
- Дашборд (`/`, `Dashboard.tsx`) — **только список**, без канбана; канбан
  живёт исключительно в `/inbox`. Это осознанное разделение (было
  реализовано и явно откачено обратно).
- `generateReportText` фильтрует `SENT`, а `groupIssues` (используется и
  дашбордом для отображения списка) — нет. Не путать эти две функции.
- Пароли агентов — по одному env var на агента (`AGENT_EROSH_PASSWORD` и
  т.д.), не общий `APP_PASSWORD`. Сессия — HMAC-токен в куке
  (`support_session`), без похода в базу на каждый запрос (`src/lib/auth.ts`).

## Рабочие привычки в этом проекте

- Автопуш в `origin/main` после каждого изменения — без лишних
  подтверждений (см. память `feedback_auto_push.md`).
- Перед пушем: `tsc --noEmit`, `eslint` на изменённые файлы, `npm run
  build`; для эндпоинтов — живой curl-тест против локального дев-сервера с
  реалистичным payload'ом и уборкой тестовых данных после.
- `README.md` держится в актуальном состоянии — при любой фиче, меняющей
  поведение, обновляй его тоже (не только код).
