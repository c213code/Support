# Support Reports — обзор проекта

Внутренний инструмент для JUZ40 (онлайн-образование), заменяющий ручное
ведение support-репорта в Telegram. Два постоянных агента — **Ерош** (это
пользователь, с которым обычно идёт работа в этом чате) и **Алпа** — плюс
общий аккаунт **Дежурный** для сменных/выходных саппортов.

## Стек

- Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS v4
- Prisma 7 (driver adapters, `@prisma/adapter-pg`) + Postgres (Vercel/Neon)
- Своя сессионная аутентификация (HMAC-подписанная кука), без NextAuth и т.п.
- Деплой на Vercel; сборка сама гоняет `prisma generate && prisma migrate deploy && prisma db seed` (см. `package.json` → `build`)

Подробности по установке/деплою/настройке Telegram-бота — см. `README.md`,
он поддерживается в актуальном состоянии и там же описано текущее поведение
каждой фичи.

## Модель данных (`prisma/schema.prisma`)

- **`Issue`** — тикет: `reportDate` (`YYYY-MM-DD`), `groupName`/`groupEmoji`,
  `position` (ручной порядок), `description`, `telegramLink`, `status`
  (`IssueStatus`), `note`, `ticketLink` (Jira/Atlassian), `createdBy`,
  таймстемпы.
- **`IssueEvent`** — история смен статуса (`from`, `to`, `actor`, `source`,
  `at`). Пишется **только** из `changeIssueStatus` (`src/lib/issueStatus.ts`)
  — единственного места, где статус вообще меняется. У `Issue` есть ещё
  `statusChangedAt`: им меряется «сколько тикет висит», и это не `updatedAt`
  (тот сдвигается от любой правки текста).
- **`IssueStatus`** enum: `SENT` (дефолт для новых тикетов) → `IN_PROGRESS` /
  `PENDING` (по сути один рабочий процесс, UI их объединяет) → `RESOLVED`.
  Метаданные статуса (лейбл, эмодзи, tailwind-классы, дефолтная заметка) —
  централизованы в `src/lib/status.ts` (`STATUS_META`).
- **`GroupPreset`** — 4 дефолтные группы поддержки с фиксированным
  порядком + `chatId` (привязка Telegram-чата к группе, заполняется один раз
  вручную через UI, дальше все сообщения из этого чата автоматически идут в
  нужную группу).
- **`TelegramMessage`** — сырые входящие сообщения из бота: `chatId` +
  `messageId` (уникальная пара), `fromId` (BigInt — id пользователей Telegram
  часто не помещаются в Int32), `text`, `usedForIssueId` (связь с
  авто-заведённым тикетом), `archived`/`viewed` флаги. Сюда же ложатся
  **собственные сообщения агентов** (сразу `archived`) — без этого нельзя
  ни посчитать, кто дежурил, ни понять, что агент уже ответил сам.
- **`AppSetting`** — синглтон (`id = "singleton"`) с рубильниками на всю
  команду: `aiCleaningEnabled`, `autoReplyEnabled`, `chatIntentEnabled`.
- **`BotReply`** — что бот сказал в рабочую группу по тикету (`chatId` +
  `messageId` + `kind` + `text`). Нужна, чтобы не повторяться и чтобы
  неудачный ответ можно было исправить/удалить — Telegram даёт это делать
  только по `message_id` и только 48 часов.
- **`GlossaryTerm`** — внутренний жаргон JUZ40 (`ДТ`, `ПФ`, `АА`),
  собранный ИИ из своей же истории. `auto = false` — вписано человеком,
  пересборка такое не трогает.
- Сессии Telegram-мастеров: **`ReviewSession`** (разбор тикетов по
  одному), **`DuplicateReviewSession`** (разбор похожих группами),
  **`PendingNotePrompt`** (ждём текст заметки реплаем),
  **`BroadcastDraft`** (объявление ждёт подтверждения),
  **`ReportSendLog`** (репорт за дату уже отправлен).

## Как это всё связано (mental model)

1. Telegram-бот шлёт апдейты на вебхук `POST /api/telegram/webhook`
   (`src/app/api/telegram/webhook/route.ts`).
2. Свои же сообщения агентов (ответы прямо в группе) отфильтровываются по
   числовому `from.id` через `OWN_AGENT_TELEGRAM_IDS` — не должны попадать в
   тикеты.
3. Если сообщения от одного и того же человека приходят с разрывом < 5 минут
   — они склеиваются в один `TelegramMessage` (и, если уже есть привязанный
   тикет, описание тикета тоже обновляется).
4. Если `chatId` уже привязан к группе (`GroupPreset.chatId`) — тикет
   заводится **автоматически**, статус `SENT`, автор `"Бот"`
   (`AUTO_ISSUE_CREATOR` в `src/lib/telegram.ts`). Если группа ещё не
   известна — сообщение просто ложится во "Входящие", группу выбирают
   вручную один раз.
5. Текст автотикета прогоняется через `cleanTicketDescription`
   (`src/lib/textClean.ts`) — чисто регулярками, без внешних API: убирает
   казахские/русские приветствия, голые ссылки, email, телефоны,
   логин/пароль строки, плейсхолдеры вложений (`[Фото]`/`[Видео]`/…) и их
   ярлыки. Если чистка оставила бы тикет пустым — возвращается исходный
   текст (лучше грязный тикет, чем пустой).
6. Как только живой агент что-то делает с авто-тикетом (меняет статус,
   редактирует) — `createdBy` молча переходит с `"Бот"` на его имя
   (server-side, по сессии — см. `PATCH /api/issues/[id]`), клиент это поле
   не присылает и не может подделать.
7. **`/inbox`** ("Входящие") — рабочее место разбора дня, вкладки
   Сообщения / **Доска** (Доска — дефолтная). Доска — канбан в 3 колонки
   (Отправлено / В работе+Пендинг / Решено), drag-and-drop между ними,
   опрос сервера каждые 15 сек (`POLL_INTERVAL_MS` в `Inbox.tsx`).
8. **`/`** (Дашборд, "Сегодня") и **`/history`** — репорт по дате: список
   тикетов по группам + живой предпросмотр текста репорта +
   "Скопировать". `generateReportText` (`src/lib/report.ts`) **исключает
   тикеты со статусом `SENT`** из текста репорта (ещё ничего не произошло —
   рано выносить), но они всё равно видны в списке на странице.
9. **Telegram — полноценный второй интерфейс, а не уведомлялка.** Сайт
   неудобен с телефона, поэтому весь день дежурного можно прожить в личке
   с ботом: `/report`, `/review` (разбор по одному), `/dedupe`, `/send`,
   `/broadcast`, `/autoreply`, `/readchat`. Вечерний cron (22:00) и
   утреннее напоминание (09:00) присылают то же самое сами.

## Бот в рабочих группах: правило одной строкой

> **Бот пишет в группу только то, чего там ещё не прозвучало.**

Из него следует всё остальное, и без него бот начинает попугайничать за
живым человеком:

| Что случилось | Что делает бот |
| --- | --- |
| Обращение пришло, никто не ответил | пишет подтверждение приёма |
| Агент ответил сам | молчит, только двигает статус |
| Статус меняют на сайте / в разборе | пишет в группу — там не знают |
| Статус изменился из-за реплики агента | **не** пишет — там уже знают |

Технически это параметр `source` (`"app"` / `"chat"`) у
`reactToStatusChange` (`src/lib/issueStatus.ts`). Забыть его = бот
отвечает агенту его же словами.

Между «бот молчит» и «бот пишет сам» есть третье состояние —
`autoReplyConfirm` (включён по умолчанию): черновик с вариантами уходит
дежурному в личку (`PendingAutoReply`, `src/lib/autoReplyApproval.ts`), и в
группу попадает только то, что человек выбрал кнопкой или написал реплаем.
Касается только подтверждения приёма: реакции на смену статуса вызывает
осознанное действие человека.

Два направления, два **отдельных** рубильника в `AppSetting` — риски
разные, и выключать одно, не трогая другое, надо уметь:
`autoReplyEnabled` (бот пишет коллегам) и `chatIntentEnabled` (бот молча
меняет то, что уйдёт в репорт боссам). Оба выключены по умолчанию.

## Что ИИ знает о проекте

Обращения написаны внутренним жаргоном (`ДТ шықпайды`, `ПФ баяу`,
`АА-ға ауыстыру`). Модель этих сокращений не знает и знать не может.
Поэтому `src/lib/projectContext.ts` держит словарь, собранный ИИ из своей
же истории решённых тикетов, и `buildAiContext()` подмешивает его в
**каждый** system-промпт в `src/lib/ai.ts`.

Частота — намеренно разная: **используется** на каждом вызове (дёшево,
из кэша), **пересобирается** раз в сутки по cron (`/api/cron/rebuild-glossary`,
19:30 UTC) плюс кнопка "Пересобрать" в панели «🧠 Словарь». Пересборка на
каждое входящее сообщение — это десятки лишних запросов к модели в день
ради данных, которые за день почти не меняются.

Ключ термина сравнивается нормализованно (регистр, тире, пробелы) — иначе
словарь копил `Backend`/`BACKEND`, `Куиз`/`КУИЗ`, четыре варианта «кодпуша»,
и каждый лишний дубль уходил в **каждый** запрос к модели. Автосборке
запрещено записывать фразы из переписки («Кеш упал, добавил временный
фоллбэк») и коды курсов с датами: термин — это слово или пара слов.

Термин, вписанный руками (`auto = false`), автосборка не перезаписывает:
если агент уточнил значение, значит модель ошиблась, и повторять её ошибку
незачем.

## Связи в базе

Все ссылки на `Issue` — настоящие внешние ключи с каскадами: `BotReply`,
`PendingNotePrompt`, `IssueEvent` удаляются вместе с тикетом, а у
`TelegramMessage` обе ссылки (`usedForIssueId`, `agentIssueId`) обнуляются —
сообщение остаётся во «Входящих» и его можно завести заново. До этого связи
держались на голых строках, и удаление тикета оставляло за собой мусор,
который чистили руками в одном месте из четырёх.

**Статус меняется только через `changeIssueStatus`.** Она делает три вещи
разом: пишет статус (+ `statusChangedAt`), переоформляет автора с `"Бот"` на
живого агента и вызывает `reactToStatusChange` с правильным `source`. Раньше
это было рассыпано по восьми местам, и один путь был помечен в коде как
«меняет статус в обход».

## Важные неочевидные вещи (грабли, на которые уже наступали)

- **Groq выводит модели из обращения, и письмо об этом легко пропустить.**
  `llama-3.3-70b-versatile`, на которой всё писалось, отключена 16.08.2026 —
  Groq предупреждал заранее по почте и рекомендовал заменой GPT OSS 120B /
  Qwen3.6 27B. Проблема не в отсутствии предупреждения, а в том, что
  снаружи это выглядит как тишина: **каждая ИИ-функция по дизайну молча
  откатывается** на regex/дефолт, поэтому пропущенное письмо = фичи просто
  перестали работать, без единой ошибки в логах. Живой список моделей:
  `GET https://api.groq.com/openai/v1/models`. Модель переопределяется
  переменной `GROQ_MODEL` — чинится без деплоя.
  Из двух рекомендованных взят `gpt-oss-120b`: `qwen3.6-27b` на наших же
  промптах не отдаёт валидный JSON (Groq возвращает ошибку валидации), а
  на JSON держатся поиск дублей и сборка словаря.
- **Текущая модель — reasoning-типа (`openai/gpt-oss-120b`), и это ломает
  маленькие `max_tokens`.** Она тратит токены на скрытые размышления
  ДО ответа: при `max_tokens: 5` (выбор из двух слов) весь бюджет уходил
  в размышления, `content` приходил пустым, и функция молча всегда
  возвращала дефолт. Лимиты должны быть с запасом (сотни токенов даже на
  ответ из одного слова), либо `reasoning_effort: "low"` для простых
  классификаций. `low` заметно тупее на разборе смысла — для описаний
  тикетов не годится.
- **`response_format: json_object` у gpt-oss требует слово "json" в самих
  сообщениях**, иначе Groq отклоняет запрос целиком. Все промпты в
  `ai.ts` это соблюдают — не вычищай оттуда упоминание JSON.
- **Описание тикета и то, что нужно для работы, — разные вещи.** Чистка
  намеренно вырезает почту, телефон и вложения: описание уходит в репорт
  боссам. Но агенту почта — единственный способ найти ученика, а «мәселе
  суретте тұр» без картинки не значит ничего. Поэтому зацепки считаются
  отдельно (`src/lib/ticketHints.ts`) и показываются **только на карточке**
  (сайт и разбор в Telegram), в `generateReportText` не попадают никогда.
- **Голый пароль отдельной строкой чистка раньше пропускала** — ловились
  только пары «пароль: X», а присылают их следом за почтой без метки, и
  пароль утекал в репорт. См. `BARE_CREDENTIAL_LINE` в `textClean.ts`:
  строка из одного токена, где есть и буквы, и цифры.
- **Подсказка ИИ, отличающаяся только грамматикой, — это шум.** Панель
  «ИИ предлагает описание точнее» сравнивала строки целиком и предлагала
  правки вроде `Оқушы құпия сөзі керек` → `Оқушының құпия сөзі керек`.
  Сравнивать надо состав слов по основам (`isCosmeticRewrite` в
  `similarity.ts`): казахский агглютинативный, окончания меняются постоянно.
- **JS `\b` не видит кириллицу.** `\b` зависит от `\w`, а `\w` по умолчанию
  ASCII-only — `\bлогин\b` тихо не матчится вообще. Для юникод-границ слова
  используй lookaround: `` (?<![\p{L}\p{N}])слово(?![\p{L}\p{N}]) `` с
  флагом `u`. См. `CREDENTIAL_PAIR` в `src/lib/textClean.ts`.
- **Автор тикета никогда не приходит от клиента** — он либо `AUTO_ISSUE_CREATOR`
  при авто-создании, либо `getCurrentIdentity()` на сервере при ручном
  создании/редактировании/auto-claim. Не добавляй `createdBy` в тело запроса
  с фронта.
- **Массовые/ретроактивные изменения данных — только через явный
  user-triggered эндпоинт + кнопку**, никогда не через миграцию, которая
  сама накатится при следующем деплое на Vercel (пример — `POST
  /api/issues/normalize-status`, `POST /api/issues/clean-descriptions`).
  Прод-миграции с `UPDATE ... WHERE ...` для данных — плохая идея, это уже
  блокировалось как небезопасное автоприменение.
- **Kanban — нативный HTML5 drag-and-drop**, без внешней библиотеки
  (`draggable` + `onDragStart`/`onDragOver`/`onDrop` в `KanbanBoard.tsx`).
- Дашборд (`/`, `Dashboard.tsx`) — **только список**, без канбана; канбан
  живёт исключительно в `/inbox`. Это осознанное разделение (было
  реализовано и явно откачено обратно).
- `generateReportText` фильтрует `SENT`, а `groupIssues` (используется и
  дашбордом для отображения списка) — нет. Не путать эти две функции.
- Пароли агентов — по одному env var на агента (`AGENT_EROSH_PASSWORD` и
  т.д.), не общий `APP_PASSWORD`. Сессия — HMAC-токен в куке
  (`support_session`), без похода в базу на каждый запрос (`src/lib/auth.ts`).
- **`callback_data` у Telegram — 64 байта.** Два cuid'а (25 символов
  каждый) туда не влезают. Поэтому "Решить так же" кладёт только id
  текущего тикета и пересчитывает подсказку в момент нажатия, а текст
  объявления для `/broadcast` лежит в `BroadcastDraft`, а не в кнопке.
- **Ответ на вопрос бота — не запрос**, и мерить его меркой запроса
  неверно. Голая почта, присланная в ответ на "пришлите почту", для
  `isNoiseOnly` — мусор (после чистки не остаётся ничего), поэтому
  `attachReplyToBotMessage` проверку на мусор намеренно не делает. Иначе
  то, что мы сами же попросили, теряется во "Входящих" без привязки.
- **Бот не видит историю чата.** Bot API отдаёт только то, что приходит
  ему вживую; `getUpdates` вдобавок заблокирован активным вебхуком.
  Единственный источник прошлой переписки — своя же таблица
  `TelegramMessage`.
- **Свои сообщения бота** удаляются и редактируются только 48 часов
  (лимит Telegram). Править лучше, чем удалять: удаление ничего не
  исправляет для того, кто уже прочитал.
- **Экраны бота нельзя множить.** Разбор по одному переписывает одно
  сообщение через `editMessageText`, а не шлёт новые: версии "баббл на
  каждый тикет" и "сетка кнопок под списком" обе были сделаны и обе
  выброшены как нечитаемые на 10+ тикетах.
- Управление ботом (кнопки "удалить ответ" и т.п.) живёт **на сайте и в
  личке**, никогда не в рабочей группе — там его увидят и нажмут коллеги.

## Рабочие привычки в этом проекте

- Автопуш в `origin/main` после каждого изменения — без лишних
  подтверждений (см. память `feedback_auto_push.md`).
- Перед пушем: `tsc --noEmit`, `eslint` на изменённые файлы, `npm run
  build`; для эндпоинтов — живой curl-тест против локального дев-сервера с
  реалистичным payload'ом и уборкой тестовых данных после.
- `README.md` держится в актуальном состоянии — при любой фиче, меняющей
  поведение, обновляй его тоже (не только код).
- **Живой тест против настоящего Telegram** — обязателен для всего, что
  этого Telegram касается. Схема: сделать копию `.env` → временно вписать
  реальный `TELEGRAM_BOT_TOKEN` и тестовые `OWN_AGENT_TELEGRAM_IDS` /
  `AGENT_TELEGRAM_IDS` → поднять `npm run dev` → бить в
  `POST /api/telegram/webhook` реалистичными апдейтами → **вернуть `.env`
  из копии и проверить, что вернулся**. Тестовые скрипты пишутся в корень
  проекта (из `/tmp` не резолвятся импорты `@/…`) и удаляются после.
- Тестовые данные — с явным префиксом (`ТЕСТ-…`) и удалением в конце.
  Реальные тикеты в локальной базе трогать нельзя: на них проверяются
  подсказки и словарь.
- Новые фичи, меняющие поведение наружу, катятся **выключенными** и
  включаются человеком (см. `autoReplyEnabled`, `chatIntentEnabled`).
